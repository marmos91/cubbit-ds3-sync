# Phase 13.1 Plan 02: Orphan Sweep Freshness Backstop Summary

Closes Phase 13.1 Finding 4 by gating `OrphanSweeper.sweep` deletes behind a
`MetadataStore` lookup that catches uploads BFS missed. Restores THUMB-19
conformance (orphan sweep correctness) and removes a confirmed data-loss vector.

## What Shipped

**Fix A** from `.planning/debug/phase13-orphan-sweep-deletes-valid.md`:

- `OrphanSweeper` gains stored `metadataStore: MetadataStore` and `driveId: UUID`
  properties. The sweep predicate now requires BOTH (a) the implied original
  is absent from `enumeratedKeys` AND (b) `metadataStore.itemExists(byKey: ...)`
  returns `false`. Either gate saying "present" preserves the thumbnail.
- `BreadthFirstIndexer.orphanSweeper` lazy init wires the new constructor and
  additionally gates on a non-nil `metadataStore`.
- `OrphanSweeping` protocol unchanged — the backstop is internal to the
  concrete `OrphanSweeper`. Existing mocks in `BFSThumbnailHookTests` continue
  working without updates.
- Same-file Sendable conformance (`extension OrphanSweeper: OrphanSweeping {}`)
  preserved.
- Data-loss-safe default: any `MetadataStore` lookup error skips the delete and
  logs at `.warning` (the next BFS pass retries; never delete on uncertainty).
  Error log uses `String(describing: error)` per Phase 13.1 Finding 5 pattern.

**Regression-lock test** (D-04):
`testSweepDoesNotDeleteThumbnailWhenSyncedItemExistsForOriginal` seeds a
`SyncedItem` for an original whose key is empty in `enumeratedKeys`; asserts
`deleted == 0` and `mock.deletedKeys == []`. This is the canonical reproduction
of the audit symptom — without the fix, this test fails because the sweep would
delete the thumbnail as a false-positive orphan.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] DS3DriveProvider cannot call internal `findItem(byKey:driveId:)`**

- **Found during:** Task 1 (writing the actual call site)
- **Issue:** The plan's `<action>` template specifies
  `try await metadataStore.findItem(byKey: originalKey, driveId: driveId) != nil`,
  but `findItem(byKey:driveId:)` is declared without `public` in
  `MetadataStore.swift` and lives in the `DS3Lib` module. `OrphanSweeper.swift`
  is in the `DS3DriveProvider` target — a different module — so the symbol is
  not reachable.
- **Fix:** Use the public Sendable-safe wrapper `MetadataStore.itemExists(byKey:driveId:)`
  from `MetadataStore+Queries.swift:11-13`, which is a one-line
  `findItem(byKey:driveId:) != nil` adapter — semantically identical to the
  plan's intent. Documented the substitution in a comment block in
  `OrphanSweeper.sweep` so the audit trail mentions both names.
- **Files modified:** `DS3DriveProvider/OrphanSweeper.swift`
- **Commit:** a9f914d

## Concurrency Review (D-05)

Three concurrency seams touched, as the debug doc's `specialist_hint`
predicted:

1. **BFS pass-tail orchestration** — `BreadthFirstIndexer.orphanSweeper` lazy
   init now requires `metadataStore`, captured at indexer construction time
   (already a stored, optional `MetadataStore` reference; no new sharing).
2. **MetadataStore query from a fire-and-forget Task** — the sweep runs
   inside `BFSThumbnailHookRunner`'s `sweepTask` (`Task { _ = await sweeper.sweep(...) }`).
   `MetadataStore` is a `@ModelActor`, so `itemExists(byKey:driveId:)` hops to
   the actor and returns a `Bool` (Sendable). No data races; query is
   serialized by the actor.
3. **Sweep iteration loop** — per-candidate `await metadataStore.itemExists(...)`.
   Sequential within the loop body; no concurrent fan-out, so no contention
   beyond what the `for` loop's other awaits (`deleteThumbnail`) already
   imposed.

Whole-project build succeeds under the project's Swift 6 strict-concurrency
configuration. CI Xcode 16.2 verification still required at PR time per the
project memory note.
