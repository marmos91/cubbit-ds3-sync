### Reproduction 3 — Finding 2 (renderer eager-snapshot)

**Why this is first:** the renderer fix (Plan 13.1-04) is the lowest-risk and most isolated; running it first establishes baseline drive health for the more interactive scenarios.

**Setup:**

1. Build & run the macOS app via Xcode (Cmd+R) against a Cubbit DS3 drive with thumbnails enabled.
2. Verify the drive mounts and Finder enumerates the root.
3. Have ready 8 raster files: 3 PNG, 3 JPG, 2 HEIC. Sizes 1–10 MB each. PNG/JPG MUST always render; HEIC is allowed to have orientation-quirky failures (separate concern, NOT Finding 2).

**Steps:**

1. Open Finder on the Drive folder.
2. Bulk-select all 8 files in another Finder window and drag-paste them into the Drive folder simultaneously (single drop event so the upload-hooks fire concurrently).
3. Wait ~30s for upload-hooks + cascade to complete.
4. Verify in S3 (via `aws s3 ls` or Cubbit console): ≥ 7 of 8 thumbnails exist under `<prefix>/.thumbnails/<filename>.jpg`.
5. Capture logs:
   ```bash
   /usr/bin/log show --last 5m --info --debug \
     --predicate "subsystem == 'io.cubbit.DS3Drive.provider'" \
     --style compact 2>&1 | grep -i "render returned nil"
   ```
6. **PASS criterion:** No PNG or JPG file in the bulk paste appears in the `render returned nil` grep. ≥ 7 of 8 thumbnails present in S3. Audit baseline was 2/8; the regression test (`testRenderJPEGSurvivesBulkPasteFanout`) already confirms 8/8 deterministically — this manual run is the real-world cross-check.

### Reproduction 4 — Finding 4 (orphan sweep MetadataStore freshness backstop)

**Setup:**

1. Continue with the same drive session from Reproduction 3.
2. The drive should now have a moderate file count after the bulk paste (≥ 30 files in some folder for a meaningful BFS pass duration).

**Steps:**

1. Trigger a long BFS pass — either wait for the next scheduled pass, or restart the extension to force one. Watch logs for:
   ```bash
   /usr/bin/log stream --predicate "subsystem == 'io.cubbit.DS3Drive.provider'" --info --debug --style compact 2>&1 | grep -E "BFS|orphan-sweep"
   ```
   Confirm "BFS pass starting" log line appears.
2. **While the pass is in flight** (BEFORE "BFS pass complete" log line), paste a fresh raster image into a folder BFS has already visited (i.e., enumerated earlier in the pass). The upload-hook will create a thumbnail for the new file.
3. Wait for "BFS pass complete" log line, then capture the next 30s of logs:
   ```bash
   /usr/bin/log show --last 1m --info --debug \
     --predicate "subsystem == 'io.cubbit.DS3Drive.provider'" \
     --style compact 2>&1 | grep -i "orphan"
   ```
4. **PASS criterion:**
   - NO log line `Orphan sweep deleted N orphan thumbnails` mentions the freshly-pasted file's S3 key.
   - The thumbnail exists in S3 under `<prefix>/.thumbnails/<freshfile>.jpg`.
   - Finder shows the thumbnail for the freshly-pasted file.
5. **FAIL criterion (Finding 4 recurrence):** the thumbnail for the freshly-pasted file is deleted by the post-pass orphan sweep, OR Finder shows a generic icon, OR S3 no longer contains the thumbnail object. If this happens: paste the log slice and the affected key into the [Reproduction Results](#reproduction-results) section below as FAIL and stop the gate run.

### Reproduction 5 — Finding 5 (rename cascade NoSuchKey demote)

**Note on environment:** post Plan 13.1-02, the orphan sweep should not pre-delete thumbnails on the steady-state path. To still trigger the rename-NoSuchKey case, this reproduction MANUALLY deletes the source thumbnail to force the cascade-rename copy to throw NoSuchKey.

**Steps:**

1. Pick one specific raster file from Reproduction 3 — say `bulk-paste-3.png`. Confirm its thumbnail exists at `<prefix>/.thumbnails/bulk-paste-3.png.jpg` in S3.
2. Manually delete the thumbnail object via the Cubbit console or AWS CLI:
   ```bash
   aws --endpoint-url https://s3.cubbit.eu s3 rm s3://<bucket>/<prefix>/.thumbnails/bulk-paste-3.png.jpg
   ```
3. In Finder, rename `bulk-paste-3.png` → `bulk-paste-3-renamed.png`. The cascade-rename will fire and try to `copyObject` from the (now-missing) source thumbnail to the new key.
4. Capture logs immediately:
   ```bash
   /usr/bin/log show --last 2m --info --debug \
     --predicate "subsystem == 'io.cubbit.DS3Drive.provider'" \
     --style compact 2>&1 | grep -i "cascade"
   ```
5. **PASS criteria (all required):**
   - The cascade-rename log line is at `.info` level (compact-output marker ` I `, NOT ` E ` for error).
   - It contains a human-readable AWS error code (`noSuchKey:` / `NoSuchKey`), NOT the opaque `SotoS3.S3ErrorType error 1` form.
   - It contains the message "source thumbnail already absent; marking new key .pending".
   - The NEW originalKey (`bulk-paste-3-renamed.png`) shows `thumbnailStatus = .pending` in MetadataStore (visible via debug surface, or implicit from BFS-tail backfill picking it up shortly after).
6. **FAIL criterion:** any of the above missing — paste the log slice (with PII redacted) into [Reproduction Results](#reproduction-results) as FAIL.

### Reproduction 6 — Parent-folder progress propagation (THUMB-13)

**Reference reproduction recipe:** `.planning/debug/phase13-parent-folder-stuck-on-child-failure.md` `## Symptoms.reproduction`.

**Steps:**

1. Pick a cloud-only file in a non-empty folder on the drive (the bulk-paste folder from Reproduction 3 works). Confirm the file is cloud-only (icon shows the cloud overlay, not synced).
2. Open Finder on the parent folder in icon view (so you can watch the parent folder's icon decoration in the breadcrumb / sidebar).
3. Double-click the cloud-only file to start a `fetchContents` download.
4. **Mid-download** (within the first ~30%), force a failure via ONE of:
   - **Option A:** Turn off Wi-Fi (System Settings → Wi-Fi → Off).
   - **Option B:** Force-quit the extension via Activity Monitor (`DS3DriveProvider`).
   - **Option C (server-side, if you have CLI access):** Move the file to a different key from another client — forces a 404 on the in-flight GET.
5. Watch the parent folder's spinner decoration. **PASS criterion:** within ONE sync cycle (~10s), the parent folder transitions OUT of the in-progress (spinner) state. The error decoration may then appear on the child (and ideally the parent), driven by `markItemAndParentAsError`.
6. Capture logs:
   ```bash
   /usr/bin/log show --last 2m --info --debug \
     --predicate "subsystem BEGINSWITH 'io.cubbit.DS3Drive'" \
     --style compact 2>&1 | grep -E "Download failed|fetchContents|progress"
   ```
7. **FAIL criterion:** spinner persists indefinitely (until next full enumeration, several minutes later). If observed, paste the log slice and screenshot of the stuck spinner into [Reproduction Results](#reproduction-results) as FAIL.
