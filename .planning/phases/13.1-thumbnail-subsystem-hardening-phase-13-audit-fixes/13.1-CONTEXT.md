# Phase 13.1: Thumbnail subsystem hardening - Phase 13 audit fixes - Context

**Gathered:** 2026-04-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix the four bugs surfaced by the Phase 13 manual audit on 2026-04-27 so the macOS thumbnail subsystem is correct under real-world load before iOS Phase 14 begins. Three findings (Findings 2, 4, 5) are root-caused with code-line precision in `.planning/debug/`; the fourth (parent-folder progress stuck) needs root-cause investigation as part of this phase.

In scope:

1. **Finding 4** — `OrphanSweeper` stale-snapshot race that false-positive-deletes valid thumbnails (data-loss).
2. **Finding 5** — Rename-cascade Soto error log opacity (`error.localizedDescription` produces "SotoS3.S3ErrorType error 1") + .error-level noise on expected NoSuchKey when source already swept.
3. **Finding 2** — `ThumbnailRenderer.renderJPEG` returns nil for valid PNG/HEIC across upload-hook + backfill paths (UX bug).
4. **Parent-folder progress stuck** — when a child `fetchContents` fails, the parent folder icon stays in the in-progress state instead of reflecting the child's error.

Out of scope:

- **Cold-folder UX hybrid path** (Finding 7) — explicitly deferred to Phase 13.2 per `finding-07-cold-folder-ux-decisions.md`.
- **Zeroed historical S3 objects** (Finding 6) — resolved as not-this-codebase (corruption predates the repo by ~3 months); Phase 14 may add a discovery tool.
- New thumbnail features, new requirements, or scope additions to THUMB-01..THUMB-26.

<decisions>
## Implementation Decisions

### Finding 4 — OrphanSweeper stale-snapshot race

- **D-01:** Adopt **Fix A** from `.planning/debug/phase13-orphan-sweep-deletes-valid.md` — `OrphanSweeper.sweep` consults `MetadataStore` as a freshness backstop before deleting a candidate orphan.
- **D-02:** New predicate: a thumbnail is deleted only when BOTH (a) its implied original key is absent from `enumeratedKeys` AND (b) `MetadataStore` has no `SyncedItem` row keyed by that original. The `MetadataStore` lookup is O(1) per candidate; uses data the upload-hook (Plan 13-07) already writes synchronously alongside the original PUT.
- **D-03:** Do NOT pursue Fix B (per-item HEAD), Fix C (re-list at sweep time), or Fix D (skip first pass-tail sweep). Fix A is sufficient on its own; the others were considered and rejected as overkill or slow.
- **D-04:** Add a 7th `OrphanSweepTest` per the debug doc's "Corrected predicate" recommendation: seed a `SyncedItem` in a mock `MetadataStore` for an original whose key is NOT in `enumeratedKeys`; assert the sweep does NOT delete the corresponding thumbnail. This is the regression lock for the audit symptom.
- **D-05:** The fix touches three concurrency seams (BFS pass-tail orchestration, `MetadataStore` query from a fire-and-forget Task, sweep iteration) — `swift-concurrency` review is expected during code review per the debug doc's `specialist_hint`.

### Finding 5 — Rename cascade log opacity + NoSuchKey noise

- **D-06:** Codebase-wide sweep for Soto-error log opacity. Audit every catch over Soto throws across `DS3DriveProvider/` and `DS3Lib/Sources/DS3Lib/` and replace `error.localizedDescription` (which dispatches through Foundation's `Error` bridge and yields "SotoS3.S3ErrorType error 1") with either `String(describing: error)` (dispatches through `S3ErrorType.CustomStringConvertible` to yield "noSuchKey: The specified key does not exist.") or a richer combined formatter using `DS3S3Client.s3ErrorCode(from:)` plus the original message. Prevents the same opacity bug from biting other surfaces in the future.
- **D-07:** In `FileProviderExtension+ThumbnailCascade.swift` rename-cascade catch, branch on `DS3S3Client.isNotFoundError(error)` and log at `.info` (not `.error`) for the "source already missing" case. NoSuchKey here is expected when orphan sweep ran against the new pass-tail concurrency window — it is not a bug post-Finding-4 fix, and the `.pending` fallback handles it correctly. Logging at `.error` creates noise.
- **D-08:** The cascade behavior itself is unchanged — the `.pending` fallback stays as defense-in-depth for genuine races (e.g., concurrent user delete + rename). Only the logging changes.

### Finding 2 — Renderer returns nil for valid raster files

- **D-09:** Apply the **eager Data snapshot** fix as primary. Replace `CGImageSourceCreateWithURL(localURL, options)` (lazy URL-backed reads) with `Data(contentsOf: localURL, options: .mappedIfSafe)` + `CGImageSourceCreateWithData(data, options)` so the image bytes are eagerly snapshotted at renderer entry. Removes the URL-lifetime dependency that the upload-hook path triggers when FileProvider releases temp URLs after `createItem` returns.
- **D-10:** Keep `kCGImageSourceShouldCache: false` for memory safety, but pair it with `kCGImageSourceShouldCacheImmediately: true` only on the thumbnail-create call (not the source-create call) — the option-flag interaction is suspect per the debug doc's investigation plan; the planner will validate via tests, not by assumption.
- **D-11:** Add three regression tests in `ThumbnailRendererTests` covering the audit symptoms: (a) bulk-paste fanout — render 8 raster files within a 100ms window, all must succeed; (b) re-render of identical bytes — render the same HEIC twice with a delay between calls, both must succeed; (c) backfill path — render from a renderer-owned temp file (the coordinator's path), must succeed for cloud-only originals.
- **D-12:** **Investigation contingency**: if the eager-Data-snapshot fix does NOT make all three regression tests pass, the planner inserts a root-cause investigation plan that enumerates every nil-return path in `ThumbnailRenderer.swift` (URL invalidation vs UTI rejection vs decode failure vs thumbnail-create failure) BEFORE shipping a partial fix. The Finding 2 debug doc is still in `status: investigating` — treating the snapshot fix as a hypothesis, not a foregone conclusion.

### Parent-folder progress stuck on child failure

- **D-13:** Spawn a root-cause spike as the **first plan** in Phase 13.1. The spike reads the relevant code paths (likely `FileProviderExtension+fetchContents` plus the parent-folder progress propagation in `S3Enumerator` / FileProvider state machine), reproduces the symptom on a real drive, and writes `.planning/debug/phase13-parent-folder-stuck-on-child-failure.md` to root-cause precision before any fix is planned.
- **D-14:** Once root cause is documented, the planner adds a fix plan in a later wave. The fix MUST propagate child error state to the parent folder icon (per the existing memory note: "propagate error to parent folder icon"). Test coverage: regression test that asserts a parent folder transitions out of in-progress state when any child fetch fails.
- **D-15:** If the spike reveals the bug is non-trivial or requires a different subsystem, the planner has authority to flag it for split-out into a 13.2 phase rather than blocking 13.1 ship. This decision is the planner's based on spike findings.

### Test coverage policy

- **D-16:** Each finding gets a unit test + targeted regression test pinning the audit symptom. No new integration tests in 13.1 — the Phase 13-11 smoke suite (`Phase13IntegrationSmokeTests.swift`) already exercises the integrated upload → cascade → fetch flow.
- **D-17:** No TDD-RED-then-GREEN gating per Phase 13's Wave 0 pattern. The audit reports already document the symptom and reproduction — the regression tests pin behavior, but they don't have to be written as a separate plan first. Each fix plan includes its own test in a single atomic commit.

### Ship criterion

- **D-18:** Phase 13.1 ships only after manual re-run of all four audit scenarios fails to reproduce the original symptoms — same gate as Phase 13-11's human-verification step. Each finding's plan ends with a "Manual repro check" task whose acceptance criterion is a fresh log capture showing the bug does not recur.
- **D-19:** Reproductions to re-run on a real drive (per the original audit timeline 2026-04-27 15:06–15:20Z):
  - Finding 4: paste a file into a folder while a long BFS pass is in flight; assert the new thumbnail is NOT deleted by pass-tail sweep.
  - Finding 5: rename a raster file whose source thumbnail was just swept; assert log line is human-readable AND at .info level for NoSuchKey.
  - Finding 2: bulk-paste 8 raster files; assert ≥ 7 of 8 thumbnails render successfully (HEIC-render-failure for orientation-quirky files is a separate concern, but PNG/JPG must always render).
  - Parent-folder: induce a child fetch failure; assert parent folder icon clears its in-progress state within one sync cycle.

<specifics>
## Specific Ideas

- The audit was performed manually with a real drive on 2026-04-27 between 15:06Z and 15:20Z. The log capture from that session is the gold reference — fixes must close the bugs that timeline exposed without breaking anything Plan 13-11 smoke tests already cover.
- Finding 5b's diagnostic improvement is high-leverage low-cost: the user-visible win is that future operators (and we) can see "noSuchKey: The specified key does not exist." in logs instead of the generic Foundation-bridge "error 1" form. This is the kind of fix that pays back on every future Soto-error debugging session.
- The Finding 4 fix's `MetadataStore` lookup must reuse the existing actor / query surface — do NOT introduce a new persistence path. Plan 13-07's upload-hook already writes the `SyncedItem` row before the original PUT returns; that's the data we're consulting.
- The Finding 2 eager-snapshot fix uses `Data(contentsOf: .mappedIfSafe)` not `Data(contentsOf:)` — `.mappedIfSafe` keeps memory pressure bounded (mmap when possible, eager copy when the file is on a non-mappable filesystem like FileProvider's temp dir). This matches Phase 12's renderer memory-safety posture.

<code_context>
## Existing Code Insights

### Reusable Assets
- `MetadataStore` (DS3Lib) — actor-isolated SwiftData store with O(1) `SyncedItem` lookups by S3 key. Used by Finding 4 fix as the freshness backstop.
- `DS3S3Client.s3ErrorCode(from:)` and `isNotFoundError(_:)` (DS3Lib/Sources/DS3Lib/DS3S3Client.swift:374-382) — the canonical helpers for Soto error introspection. Finding 5 logging sweep must use these instead of inventing parallel introspection.
- `Data(contentsOf:options:.mappedIfSafe)` — Foundation primitive that gives bounded memory while eagerly snapshotting bytes. Replaces `CGImageSourceCreateWithURL` in Finding 2 fix.
- `Phase13IntegrationSmokeTests.swift` (Plan 13-11) — existing test scaffold that exercises upload-hook → fetch → cascade flows. 13.1 fixes must NOT regress this; they may extend it but the policy is unit + targeted regression only.

### Established Patterns
- **Same-file Sendable conformance** (Plan 13-09 pattern) — `extension OrphanSweeper: OrphanSweeping {}` lives in `OrphanSweeper.swift` to satisfy Swift 6 strict concurrency. The Finding 4 fix must keep this layout when it adds the `MetadataStore` dependency.
- **Free `@Sendable` functions for hooks** (Plan 13-07/13-08 pattern) — bypasses Pitfall 1 (FP extension non-Sendable subclass) by avoiding `self` capture. The Finding 4 fix likely keeps `OrphanSweeper.sweep` as the actor entry point but the `MetadataStore` query inside is a free function.
- **Defense-in-depth fallbacks** (Plan 13-08 pattern) — rename cascade marks new key `.pending` instead of failing. Finding 5b's logging change preserves this fallback; only log severity + format change.
- **Deviation comments in plans** (Plan 13-08 example: "free `@Sendable` functions vs literal extension-method form") — when the Finding 4 fix shape diverges from `OrphanSweepTests.swift`'s mock-injection style, document the deviation in the plan.

### Integration Points
- Finding 4 fix lands at `DS3DriveProvider/OrphanSweeper.swift:91` (the predicate). The `MetadataStore` reference enters via constructor injection or a new `OrphanSweeperContext` Sendable bundle (planner's choice). Test seam: `OrphanSweepTests.swift` already injects mocks; new test extends that pattern.
- Finding 5 fix lands at `DS3DriveProvider/FileProviderExtension+ThumbnailCascade.swift:118-128` (rename catch) and `:142` (delete-old catch). Codebase-wide sweep extends to every Soto-throws catch in `DS3DriveProvider/` + `DS3Lib/Sources/DS3Lib/`.
- Finding 2 fix lands at `DS3Lib/Sources/DS3Lib/Thumbnails/ThumbnailRenderer.swift` (renderer entry point). Call sites that pass `localURL` (`ThumbnailUploader.swift`, `ThumbnailBackfillCoordinator.swift`, upload-hook) are unaffected — the contract change is internal.
- Parent-folder spike target: TBD by spike. Likely candidates per the v3.1 architecture: `S3Enumerator.swift` (folder enumeration progress), `FileProviderExtension+fetchContents.swift` (per-item fetch), or the `NotificationManager._activeOperations` counter (per `auto-memory: NotificationManager Operation Counter`).

### Constraints
- **Swift 6 strict concurrency** — every change must compile under the project's `Sendable` rules. Local builds are looser than CI Xcode 16.2; verify on CI.
- **NSFileProviderErrorDomain / NSCocoaErrorDomain only** (CLAUDE.md File Provider Error Handling) — Finding 5 logging changes must not change error domains returned from FileProvider methods. Logging is internal; error returns are still gated.
- **OSLog `privacy: .public`** on dynamic strings (per project memory) — Finding 5's new richer log strings (e.g., `String(describing: error)`) MUST mark error content `privacy: .public` so it appears in system logs.
- **No new requirements** — Phase 13.1 doesn't amend THUMB-XX. The bugs violate existing requirements (THUMB-13 error mapping, THUMB-19 orphan sweep correctness); fixes restore conformance, they don't extend the contract.
