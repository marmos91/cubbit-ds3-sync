# Phase 17.3: Windows Enumeration Performance & UX - Context

**Gathered:** 2026-07-07
**Status:** Ready for planning — scope signed off 2026-07-07 (D-04 aggregate counts; D-06 include minimal anchor; local MSVC build)

<domain>
## Phase Boundary

Make Windows prefix enumeration **correct and responsive at scale**: browsing a prefix with thousands of objects populates Explorer incrementally with low time-to-first-visible-item, repeated enumerations and remote changes never produce duplicate / missing / ghost entries, and enumeration + hydration progress is observable to the user while bounded concurrency keeps S3 from throttling (`SlowDown`).

**Guiding principle (carried from 17.1, user directive 2026-06-01): follow the same UX/behavior as macOS.** The Apple File Provider `S3Enumerator` (`apple/DS3DriveProvider/S3Enumerator.swift`) is the canonical reference for paged streaming enumeration, prune-only-on-single-page, and the sync-anchor cursor. Windows should mirror it, not invent a new model.

**Root causes being fixed** (from the 2026-07-07 recon; file:line evidence in `17.3-RESEARCH.md`):

1. **Poll reads only the first page.** `SyncEngine.PollOnceAsync` (`windows/DS3Drive.Sync/SyncEngine/SyncEngine.cs:121`) issues one `ListObjectsListing(bucket, prefix, "/", continuationToken: null)` and never consults `IsTruncated` / `NextContinuationToken`. A prefix with >2000 direct children (`LIST_BATCH_SIZE = 2000`) sees only page 1; because the diff treats absent remote keys as deletions (`ApplyDeltaAsync`, `SyncEngine.cs:264`), every object beyond page 1 is computed as `Deleted` and pruned. **Correctness/data-loss bug — highest priority.**
2. **Enumeration buffers the whole level, then emits one batch.** `PlaceholderMaterializer.ListLevel` (`PlaceholderMaterializer.cs:71`) loops the continuation token to completion into memory before a single `CfCreatePlaceholders` / `TransferPlaceholders` call — no streaming to Explorer as pages arrive, unlike macOS `observer.finishEnumerating(upTo: nextPage)` (`S3Enumerator.swift:123`).
3. **Ghost removal deletes the DB row only.** `ApplyDeltaAsync` deletes the `placeholders` row for `delta.Deleted` but never issues an on-disk `CfDeletePlaceholders` — a failed cascade or external bucket edit can leave a ghost placeholder in Explorer.
4. **No quantitative progress.** `DriveStatus` is Idle/Syncing/Paused/Error only; `DriveStatusChange` deliberately carries no file names or counts (STRIDE T-17-10-05). Users see a spinner, not "X of Y" / percent.
5. **Enumeration/listing is unbounded and uninstrumented.** The `SemaphoreSlim(20,20)` limiters gate only per-object fetch/upload (`CfApiProvider.cs:40`, `UploadQueue.cs:29`); the listing token-loop has no concurrency cap or progress hook. macOS has a dedicated `BucketListingLimiter`.

**In scope:** the 3 locked success criteria in `ROADMAP.md` §"Phase 17.3":
  1. Thousands of objects enumerate incrementally (paged) with low time-to-first-visible-items and no UI freeze.
  2. Placeholder creation/refresh idempotent across repeated enumerations and remote changes — no duplicates, missing, or ghosts.
  3. Enumeration + hydration progress observable (status column / tray); bounded concurrency prevents `SlowDown`.

**Out of scope (later phases):**
  - Thumbnails in Explorer — Phase 17.2.
  - Full settings surface, drive stats detail UI, pause/resume UI, recent files, transfer-speed readout — Phase 17.5 (17.3 may *emit* the progress signal these later consume, but does not build their UI).
  - Cross-FFI structured logging / error-surface hardening — Phase 18 (POL-01/02).
  - Installer / release / CI pipeline — Phase 17.6.
</domain>

<decisions>
## Implementation Decisions

### Enumeration correctness (criteria 1 + 2)
- **D-01 (the critical fix):** `SyncEngine.PollOnceAsync` must consume the **full** remote listing before computing the diff — loop `NextContinuationToken` until `IsTruncated == false` (mirroring macOS `listAllRemoteChildren()`, `S3Enumerator.swift:280`) — so `Deleted` is only ever computed against the complete remote set. No object beyond page 1 may be misclassified as a deletion. Covered by a regression test that seeds >2000 keys.
- **D-02 (incremental streaming):** Rework the placeholder-creation path (`PlaceholderMaterializer.ListLevel` + `FetchPlaceholdersHandler`) to emit placeholders **per page as pages arrive** rather than buffering the whole level, mirroring macOS per-page `finishEnumerating(upTo:)`. Idempotency preserved by the existing `(drive_id, s3_key)` upsert (`PlaceholderStore.cs:56`) + on-disk `ERROR_ALREADY_EXISTS` tolerance (`PlaceholderMaterializer.cs:275`). The exact cfapi paging handshake (successive `CF_OPERATION_TRANSFER_PLACEHOLDERS` with a "more coming" completion status vs. repeated `CfCreatePlaceholders`) is a Claude's-discretion research item for the plan.
- **D-03 (ghost removal):** On `delta.Deleted`, `ApplyDeltaAsync` must remove the **on-disk placeholder** (`CfDeletePlaceholders` / equivalent), not just the DB row, so Explorer never shows a ghost whose original is gone. Placeholder identity stays the full S3 key (stable across re-enumeration).

### Progress + concurrency (criterion 3)
- **D-04 (progress signal — SIGNED OFF: aggregate counts, no names):** Surface enumeration + hydration progress as an **aggregate, file-name-free** signal — opaque counts only ("items enumerated", "items total-or-indeterminate", "bytes hydrated"), never file names or per-file identity — so criterion 3 is met without violating STRIDE T-17-10-05 (which bans *file names*, not aggregate numbers). Recommended shape: a **separate `EnumerationProgress` event** on the broadcaster rather than widening the `DriveStatus` enum, keeping the status reducer clean. Surfaced in the tray now; status-column wiring optional.
- **D-05 (bounded listing):** Add a listing concurrency bound (parity with macOS `BucketListingLimiter`) so recursive/large enumerations cannot fan out unbounded `ListObjectsV2` calls and trip `SlowDown`. Keep the existing `SemaphoreSlim(20,20)` for fetch/upload. Page size stays 2000 (`LIST_BATCH_SIZE`, macOS parity) unless research shows a smaller first page materially improves time-to-first-item — in which case expose the `max_keys` override already plumbed through the FFI (`DS3DriveS3Client.cs:107` currently hardcodes `0`).

### Efficiency (optional)
- **D-06 (sync-anchor cursor — SIGNED OFF: include minimal anchor):** Windows re-lists + full-diffs every 60s poll; macOS uses a `NSFileProviderSyncAnchor` hash over `key→etag` (`S3Enumerator.swift:63`) to short-circuit when nothing changed. Introduce a minimal Windows anchor (hash the per-prefix `key→etag` set, persist per prefix, skip `ApplyDelta` when the hash is unchanged), mirroring macOS `currentSyncAnchor`. Efficiency win layered on top of the D-01 full-pagination fix — the anchor is computed over the *complete* listing, never a single page.

### Verification
- **D-07:** Two-layer, matching 17.1:
  1. **Automated tests** — a >2000-key pagination regression for D-01 (unit/integration, `Category=Integration` gated on Cubbit secrets like the existing "C# P/Invoke Tests (Windows)" job); idempotency test re-running enumeration twice asserts no duplicate rows/placeholders; ghost-removal test asserts `CfDeletePlaceholders` on delete.
  2. **Manual ARM64 smoke** — a `manual-smoke-*.md` checklist covering a large-prefix drive (thousands of objects): incremental appearance, no freeze, progress visible in tray, no ghosts after a remote delete.

### Claude's Discretion
