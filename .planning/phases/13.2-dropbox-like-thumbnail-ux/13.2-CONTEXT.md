# Phase 13.2: Dropbox-like thumbnail UX - Context

**Gathered:** 2026-04-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the BFS-driven thumbnail subsystem with a reactive, Apple-API-driven model. Lean on `NSFileProviderReplicatedExtension`'s native enumeration + thumbnail re-request scheduling instead of running our own indexer, coordinator, and orphan sweeper.

**The feature is exactly three lanes — nothing more:**

1. **Priority 1 — Cache hit:** `fetchThumbnails` reads `.thumbnails/<key>.jpg` from S3 first (small, low-bandwidth — ~50 KB per item). This is the steady-state hot path.
2. **Priority 2 — Cache miss fallback:** Download the original from S3, render locally via `ThumbnailRenderer`, return rendered JPEG bytes to Finder via `perThumbnailCompletionHandler`. **User sees a thumbnail immediately** — no "wait for backfill" UX regression.
3. **Priority 3 — Background backfill PUT:** After serving rendered bytes, fire-and-forget `Task` PUTs the same JPEG to `.thumbnails/<key>.jpg` so the next visit hits Priority 1. Then `signalEnumerator(for: parentContainer)` so Apple keeps its view of the working set fresh.

This subsumes everything Phase 13 needed BFS for. The 3-lane model + cascades + upload-time generation = the whole feature.

**In scope:**
- New `ThumbnailFallbackLimiter` actor (2-slot) for the cache-miss lane (separate from existing 4-slot `ThumbnailFetchLimiter`)
- Hybrid consume-path fork in `fetchThumbnails`
- Schema migrations to drop `thumbnailFailCount` (V4) and `thumbnailStatus` (V3) properly
- Deletion of `BreadthFirstIndexer`, `ThumbnailBackfillCoordinator`, `BFSThumbnailHookRunner`, `OrphanSweeper`, `warmCacheThenStartBFS`, `runThumbnailRolloutIfNeeded` and all their tests
- Tray status reduction: `{idle, busy, error, paused}`

**Out of scope:**
- Anything beyond the 3-lane model (no proactive prefetch, no "smart" priority, no batching, no scheduling)
- iOS rendering (Phase 14 owns its `BGProcessingTask` + `ForegroundBackfillDriver`)
- Cellular gating, manual "Generate now" action, iOS Settings progress UI (Phase 14)
- Tray progress UI on macOS (THUMB-24 dropped 2026-04-25)
- Push-based change notifications from S3 (existing 30s `pollingTask` keeps doing its job)

</domain>

<decisions>
## Implementation Decisions

### Feature shape (locked spine)

- **D-01:** `fetchThumbnails` follows three lanes in strict order: (1) S3 thumbnail cache hit, (2) original-download + local render fallback, (3) async backfill PUT to `.thumbnails/<key>.jpg`. **No fourth lane. No additional optimizations.**
- **D-02:** Cached-thumb GETs use the existing 4-slot `ThumbnailFetchLimiter`. Fallback (full-original) GETs use a new 2-slot `ThumbnailFallbackLimiter` actor. Strict separation prevents heavy fallbacks from starving the cheap hot path.
- **D-03:** When `fetchThumbnails` arrives with N items and some are cache-hits, some are misses: cached items return immediately via `perThumbnailCompletionHandler`, fallback items are processed 2-at-a-time and stream completions to the same handler as they finish. Matches Phase 13's per-item handler contract.
- **D-04:** The rendered bytes returned to Finder via `perThumbnailCompletionHandler` are the **same bytes** that the async PUT writes to S3 — single render per cache-miss. No re-render for storage.

### Schema cleanup (Clean removal)

- **D-05:** Ship Schema V5 to remove `thumbnailFailCount` and `setThumbnailFailure` helper. Ship Schema V6 to remove `thumbnailStatus` field and `fetchPendingThumbnails` query.
- **D-06:** Both migrations are SwiftData "remove field" migrations — a less-trodden path; planner validates with explicit migration tests on a seeded V4 / V3 store before shipping.
- **D-07:** Migrations land **after** all consumers are deleted (i.e., after `ThumbnailBackfillCoordinator`, `BFSThumbnailHookRunner`, `OrphanSweeper` are gone). Deferring schema removal until consumers vanish prevents the build from going red mid-sequence.
- **D-08:** Upload-hook code that wrote `.notApplicable` / `.uploaded` to `thumbnailStatus` is removed in the same plan that ships Schema V6 — no orphaned writes against the dropped column.

### Launch-time work removal (Kill both completely)

- **D-09:** Delete `runThumbnailRolloutIfNeeded` entirely. Phase 11 wizard's `inspectThumbnailPrefix` at drive-add is the sole rollout trigger; per-launch re-iteration adds nothing for the cost of N ListObjectsV2 calls.
- **D-10:** Delete `warmCacheThenStartBFS` entirely, **including** the sentinel-purge logic. The sentinel purge was defensive cleanup for a pre-fix bug; it has been one-shot done on user disks by now. Any residual sentinel rows are harmless (the new code path doesn't read sentinel state).
- **D-11:** `FileProviderExtension.startBFSIndexer`, the `breadthFirstIndexer` property, invalidate teardown, and all callsites (including `prioritize(prefix:)` from `materializeFolderItem`) die with the indexer.

### Cache invalidation strategy (Just signalEnumerator)

- **D-12:** After a successful background backfill PUT, call `signalEnumerator(for: parentContainer)`. **Do NOT** encode a thumb-availability bit into `S3Item.itemVersion.contentVersion`.
- **D-13:** Rationale: the rendered bytes Apple cached during the cache-miss fallback are byte-identical to what we just PUT to S3. Re-fetching from S3 would return the same bytes. Encoding a thumb-availability bit would add in-memory state, complicate `contentVersion` derivation, and produce zero user-visible benefit.
- **D-14:** `S3Item.itemVersion.contentVersion` continues to be derived from `sourceETag` only (existing Phase 13 behavior). Modifications change ETag → `contentVersion` changes → Apple invalidates → next visit hits S3 cache.
- **D-15:** Cascades work via the new key on rename (Apple sees a fresh identifier → fresh `fetchThumbnails` call → cache hit on the new path).

### Tray status + memory safety

- **D-16:** Tray states reduce to `{idle, busy, error, paused}`. Drop `.indexing` state. The transient indexing pulses S3Enumerator emits on folder open collapse to `busy` via NotificationManager's existing aggregator — preserving the "something is happening" UX signal during slow listings.
- **D-17:** **No size cap** on the fallback path. `Data(contentsOf: .mappedIfSafe)` keeps memory bounded for large files; the 2-slot `ThumbnailFallbackLimiter` bounds peak concurrent memory at ~2 large originals. Planner adds a memory smoke test (per Open Question 6) — if metrics show jetsam pressure, a cap is added in a follow-up.
- **D-18:** Memory smoke test target: render 8 sequential 50 MB HEIC files via the fallback path; assert peak resident memory stays under 50 MB ceiling. Test lives alongside `ThumbnailHybridConsumeTests`.

### Strike counter / negative cache (THUMB-20 reframed)

- **D-19:** `ThumbnailFallbackLimiter` actor holds two pieces of state: `[String: Int]` strike counter keyed by S3 key, and `Set<String>` poison-key negative cache. Both **in-memory only, reset on extension launch**. No persistence.
- **D-20:** Increment counter on each render failure for a key. On 3rd strike, move the key into the poison set and remove from the counter. Subsequent fallback requests for poison keys return nil immediately (skip download + render entirely) until extension restart.
- **D-21:** Rationale for in-memory-only: macOS extension is long-lived (hours-days). Real-world poison files are rare (deterministic decode failures, not transient). Persisted poison sets introduce a stale-state bug surface (file gets re-uploaded with valid bytes → never gets a thumb without invalidation logic). Worst-case cost on extension restart: 3 wasted GETs per poison file. Acceptable.

### Removal sequencing

- **D-22:** Use the research's 11-step order (additive first, then deletions; build green between commits) as the **default plan layout**. Planner has authority to adjust for wave parallelization, but MUST preserve two invariants: (a) additive paths (`ThumbnailFallbackLimiter`, fallback fork, post-PUT `signalEnumerator`) ship BEFORE any BFS-stack deletion; (b) build is green at every commit.
- **D-23:** Schema migrations (D-05..D-08) are the LAST plans in the phase — they require all consumers to be already deleted.

### Pause / resume (THUMB-21 trivially satisfied)

- **D-24:** Pause is a per-handler `SharedData.isDrivePaused` check. With no BFS, there is no "backfill engine" to halt. The fallback path checks pause state before acquiring a `ThumbnailFallbackLimiter` slot; the upload hook checks before its post-PUT render. THUMB-21 needs no new code — just the gate on each lane.

### Orphan handling (THUMB-19 reframed)

- **D-25:** Cascades are the **sole** orphan prevention. The periodic orphan sweeper dies with this phase. Consequence: a cascade failure leaks one orphaned `.thumbnails/<key>.jpg` until next manual intervention. **This is acceptable** — orphans waste S3 storage, never cause data loss.
- **D-26:** No debug-menu "verify integrity" action in this phase. If power users request orphan diagnostics later, add a one-shot debug command — not a periodic sweeper.

### Claude's Discretion

- Exact memory smoke test scaffolding (XCTAssert macro choice, fixture file generation)
- Whether `ThumbnailFallbackLimiter`'s 2-slot semaphore reuses an existing actor pattern or introduces a fresh one (planner reviews `BucketListingLimiter` and `ThumbnailFetchLimiter` for the closest analog)
- Log message wording for fallback-path observability (must use `privacy: .public` on dynamic strings per CLAUDE.md)
- Test file naming (`ThumbnailHybridConsumeTests` vs `ThumbnailFallbackPathTests` etc.)

</decisions>

<specifics>
## Specific Ideas

- "Less is more." Apple does the heavy lifting; we lean on it. Anything we'd build to schedule, prioritize, or pre-walk is something Apple's framework already does reactively.
- The user's mental model: **cache hit, then fallback render, then backfill — that is the whole feature.** Anything we add beyond those three lanes is scope creep.
- The cold-folder UX bug (5-30 minute wait for BFS to chew through the bucket) goes away **structurally**, not via optimization — there is no global pass to wait for.
- The 3-strike rule survives only as an in-process safety net for the new fallback path, not as a Schema field. Persistence was wrong granularity.

</specifics>
