### Q3: Cache invalidation strategy (post-PUT signaling)

**Options presented:**
1. Encode thumb-availability into `contentVersion` + signalEnumerator (Recommended)
2. Just call signalEnumerator; rely on natural ETag eviction
3. Encode using HEAD-on-thumb at enumerate time

**User initial response:** "2 seems more correct, no? Help me choose"

**Claude's analysis (delivered to user):**
The contentVersion-bit encoding is overengineering because:
- Apple's cache from cache-miss fallback already holds bytes byte-identical to S3 (same renderer output)
- Re-fetching from S3 returns identical bytes → zero user-visible change
- File modifications already change `contentVersion` via the `sourceETag` term → Apple already invalidates correctly on the cases that matter
- Cascades work via fresh identifiers (rename) → fresh `fetchThumbnails` call
- The 30s `pollingTask` + `signalEnumerator(for: parentContainer)` after PUT is sufficient

Net: ~−20 LoC saved by dropping the in-memory bit cache. No regression in user-visible behavior.

**User final selection:** "Option 2 it is" — Just call signalEnumerator; rely on natural ETag eviction.

**Captured as:** D-12, D-13, D-14, D-15.

## Round 2 — Two follow-up questions

### Q5: Strike counter / negative cache behavior (THUMB-20)

**Options presented:**
1. In-memory only, resets on extension restart (Recommended)
2. In-memory + persisted poison set across restarts
3. Per-session with exponential backoff retry

**User initial response:** "Help me choose. I want the simplest/most effective"

**Claude's analysis (delivered to user):**
Option 1 wins on both axes:
- **Simplest:** ~10 LoC actor state, no persistence surface area, no invalidation logic
- **Most effective:** macOS extension is long-lived (hours-days). Within a session, behavior is identical to options 2/3. Worst-case cost on rare extension restart: 3 wasted GETs per poison file — negligible for typical 0-5 poison files per user.
- **Option 2 fails:** persisted poison set introduces stale-state bug (file gets re-uploaded with valid bytes → never gets a thumb without invalidation logic threaded through ETag-change paths). Solves trivial cost by adding real bug surface.
- **Option 3 fails:** exponential backoff is designed for transient network failures. Our poison failures are deterministic per file (renderer can't decode bytes X). Backoff buys nothing because the next retry fails identically.

**User final selection:** "Option 1" — In-memory only, resets on extension restart.

**Captured as:** D-19, D-20, D-21.

## Round 3 — Feature scope reaffirmation (user-initiated)

**User message (verbatim):**

> "Only thing is: Make sure we give priority to .thumbnails (since they are smaller and hit less the network), then, if they are not available, download the original image and use them as thumbnails (preserve UX). Then backfill the give image (if not present). The feature is all this. Nothing more"

**Interpretation:** explicit anti-scope-creep guardrail and confirmation of the 3-lane priority order:
1. Cache hit on `.thumbnails/<key>.jpg` (small, low-bandwidth)
2. Fallback render from original (preserve UX)
3. Background backfill PUT (if not present)

The "Nothing more" clause is a strong signal: anything beyond these 3 lanes is scope creep, including any "smart" optimizations the planner might be tempted to add.

**Captured as:** D-01, D-02, D-03, D-04 (lane order is now the spine of the phase). Reflected in `<domain>` "The feature is exactly three lanes — nothing more" framing.
