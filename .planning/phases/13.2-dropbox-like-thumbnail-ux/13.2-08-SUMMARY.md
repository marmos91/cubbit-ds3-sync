# Phase 13.2 Plan 08: Schema V5 — Drop thumbnailFailCount Summary

Shipped Schema V5 of the SyncedItem metadata model. The V5 migration drops the `thumbnailFailCount: Int = 0` field added in V4 (Phase 13 D-29); `MetadataStore.setThumbnailFailure` was deleted alongside it; the `ThumbnailUploader` no longer writes any schema strike state. The 3-strike rule lives entirely in `ThumbnailFallbackLimiter`'s in-memory state per D-19/D-20 (shipped by Plan 01). Migration validated by `SchemaV5MigrationTests` on a seeded V4 store before shipping (D-06).

## What changed

- **SyncedItem.swift** — Added `SyncedItemSchemaV5` (drops `thumbnailFailCount`); updated `SyncedItemMigrationPlan.schemas` to `[V1, V2, V3, V4, V5]`, `stages` to include `migrateV4toV5` (lightweight); pointed the public `typealias SyncedItem = SyncedItemSchemaV5.SyncedItem`. The V4 enum body is preserved verbatim (migration source). The `SyncAnchorRecord` typealias chain (V2→V3→V4→V5) is preserved per Pitfall 3.
- **MetadataStore.swift** — Bumped container schema to `Schema(versionedSchema: SyncedItemSchemaV5.self)`. `applyUpsert`'s ETag-change branch dropped the `existing.thumbnailFailCount = 0` write; the `existing.thumbnailStatus = .pending` reset survives (D-08 removes that in V6/Plan 09).
- **MetadataStore+Queries.swift** — Deleted the `setThumbnailFailure` helper entirely. Doc-comment trail in its place points at `ThumbnailFallbackLimiter`.
- **ThumbnailUploader.swift** — Render-nil path now logs + returns (no schema write). PUT-failure path logs + rethrows (no schema write); the catch block also switched from `error.localizedDescription` to `DS3S3Client.describeSotoError(error)` for consistency with the codebase-wide Phase 13.1 sweep. Doc comments rewritten to reflect the new failure semantics.
- **SchemaV5MigrationTests.swift** (NEW) — 3 tests: `testV4ToV5LightweightMigrationDropsFailCountPreservesRows` (round-trip with 3 V4 rows + 1 SyncAnchorRecord), `testTypealiasIsV5`, `testMetadataStoreV5BoundContainerRoundTrip`.
- **SchemaV4MigrationTests.swift** — Updated to fetch via `SyncedItemSchemaV4.SyncedItem` explicitly (the public `SyncedItem` typealias resolves to V5 now). Renamed `testTypealiasIsV4` → `testV4SchemaRoundTripsThumbnailFailCount` (the V4 typealias assertion no longer holds; the test now proves the V4 schema is still a viable migration source).
- **ThumbnailUploaderTests.swift** — Renamed `testGenerateAndUploadWhenRendererReturnsNilMarksFailed` → `testGenerateAndUploadWhenRendererReturnsNilLogsAndReturns`. Both test #3 and #4 now assert the row stays `.pending` (no schema strike write); repeated failures still don't transition the schema row.
- **ThumbnailStrikeRuleTests.swift** — DELETED (10 tests, ~250 LoC). Every test asserted on `thumbnailFailCount`/`setThumbnailFailure` semantics; the rule moved to `ThumbnailFallbackLimiter` (Plan 01) and is covered by `ThumbnailFallbackLimiterTests`.
- **8 other test files** — Bumped V4-bound containers to V5 (Pitfall 3 — the `SyncedItem` typealias resolves to V5 now): `MetadataStoreThumbnailQueriesTests`, `MetadataStoreMigrationTests`, `MetadataStoreTransientStatusTests`, `MetadataStorePurgeTests`, `ConflictDetectionTests`, `SyncEngineTests`, `Phase13IntegrationSmokeTests`, `UploadHookTests`, `CascadeDeleteTests`, `CascadeRenameTests`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] SwiftData "Duplicate version checksums across stages" trap**
- **Found during:** Task 2, first `swift test` of `SchemaV5MigrationTests`.
- **Issue:** `testV4ToV5LightweightMigrationDropsFailCountPreservesRows` failed with `NSInvalidArgumentException: Duplicate version checksums across stages detected.` Root cause: V5's `SyncedItem` is structurally byte-for-byte identical to V3's (V4 added `thumbnailFailCount`, V5 removed it back). SwiftData's schema-checksum machinery hashes the model fields and the version identifier (`Schema.Version(5,0,0)`) is NOT mixed into the per-stage checksum — so V3 and V5 collide. PATTERNS.md does not document this trap (it covers Pitfall 3, the `SyncAnchorRecord` typealias requirement, but not the "structurally-identical-revert" case).
- **Fix:** Added `@Attribute(hashModifier: "v5")` to `SyncedItem.s3Key` in V5 only. SwiftData mixes the `hashModifier` into the attribute's checksum, forcing V5 ≠ V3 at the schema level. Doc comment on the attribute explains why and references Phase 13.2 D-06.
- **Files modified:** `DS3Lib/Sources/DS3Lib/Metadata/SyncedItem.swift` (V5 enum body).
- **Commit:** `78bb74a`.

**2. [Rule 1 - Bug] `ThumbnailUploader` PUT-failure log used `error.localizedDescription`**
- **Found during:** Task 2 Step 5 (uploader callsite removal).
- **Issue:** The original PUT-failure catch block logged via `error.localizedDescription, privacy: .public`. CLAUDE.md / MEMORY.md mandate `DS3S3Client.describeSotoError(error)` for Soto errors — `localizedDescription` returns generic strings that hide the S3 error code. This was a pre-existing inconsistency (Phase 13.1 sweep missed it) but the surrounding code was being edited so fixing it inline costs nothing.
- **Fix:** Switched to `DS3S3Client.describeSotoError(error)`. Matches every other Soto catch in the codebase post-Phase 13.1.
- **Files modified:** `DS3Lib/Sources/DS3Lib/Thumbnails/ThumbnailUploader.swift`.
- **Commit:** `78bb74a`.
