# Phase 13.2 Research — Minimal Demand-Driven Architecture

**Researched:** 2026-04-27
**Domain:** macOS File Provider — replace BFS-driven thumbnail subsystem with reactive Apple-API-driven model
**Confidence:** HIGH on Apple framework contracts, MEDIUM on bandwidth/UX trade-offs of the simplified model
**Phase:** 13.2 (dropbox-like-thumbnail-ux)

---

## TL;DR (5 bullets)

1. **Apple's File Provider already does the indexing.** `NSFileProviderReplicatedExtension` invokes `enumerateItems` per-folder on user navigation and `enumerateChanges` on the working set — there is no need for a custom BFS pass loop, queue manager, or pass scheduler. Our `S3Enumerator` already implements both contracts correctly. **All proactive indexing in `BreadthFirstIndexer` is redundant** with what the framework already calls reactively.
2. **Apple's thumbnail cache is keyed on `NSFileProviderItem.itemVersion.contentVersion`.** Bumping `contentVersion` after writing `.thumbnails/<key>.jpg` to S3 + calling `signalEnumerator(for: parentContainer)` is the documented mechanism for telling the system "re-request the thumbnail." We do not need our own backfill scheduler; we just need one fire-and-forget render-and-bump path triggered by the `fetchThumbnails` cache miss itself.
3. **The simplest viable model has three lanes** and no background loops: (a) **upload-time generation** — already correct in Phase 13 (`createItem`/`modifyItem` post-PUT fire-and-forget); (b) **consume-time fallback** — `fetchThumbnails` cache miss returns the rendered original immediately AND fires-and-forgets the render+upload; (c) **cascades** — already correct in Phase 13 (delete + rename). **Everything else dies.**
4. **Net code change target: ~−1700 LoC deleted, ~+80 LoC added.** Delete `BreadthFirstIndexer` (~390 LoC), `BFSThumbnailHookRunner` (~180 LoC), `ThumbnailBackfillCoordinator` (~330 LoC), `OrphanSweeper` (~210 LoC), `QueueManager` extension, `wasPaused` flip detection, `BFS pass-tail hooks`, `warmCacheThenStartBFS` (~110 LoC), `prioritize(prefix:)`, `runThumbnailPassTailHooks`, plus their test files (~500 LoC). Add: a single `fetchThumbnailsConsumePath` cache-miss fork (~60 LoC) + a thin `signalEnumerator(for:)` invocation after upload completes (~10 LoC). The 3-strike rule survives **only** as a per-item local counter inside the consume-fallback path (~10 LoC), not as a Schema field.
5. **The cold-folder UX bug from Finding 7 is solved structurally.** Today users wait for a global BFS pass to traverse the entire bucket before their cold folder gets thumbnails. With the demand-driven model, opening a folder triggers `enumerateItems` (already on-demand, S3-first) + `fetchThumbnails` (already in place), and the consume-path immediately renders+caches each visible item — same wall-clock latency as Phase 13 audit's "render full image" UX. The 5-30 minute regression goes away because we never wait on a global pass.

## What Apple's File Provider gives us for free

> All claims below `[CITED]` from Apple's `FileProvider.framework` headers (mkalmes/moby Github mirror) and Apple Developer Forums. Cross-verified against `NSFileProviderEnumerating.h` SDK header.

### 1. Per-folder enumeration on demand `[CITED: developer.apple.com/documentation/fileprovider/nsfileproviderenumerating]`

The system calls `enumerator(for:request:)` → `enumerateItems(for:startingAt:)` whenever the user navigates into a folder in Finder. The framework batches and paginates through `NSFileProviderPage`. **We do not need to pre-walk the bucket.** Our existing `S3Enumerator.enumerateItems` already correctly does S3-first listing with cache fallback (lines 218-502).

**What we DON'T need to build:** a global tree-walker, BFS queue, level-by-level scheduler, prioritization logic.

### 2. Working-set change enumeration `[CITED: header doc — "Call this method either in the app or in the extension to trigger an enumeration, typically in response to a push."]`

The system calls `enumerateChanges(for:from:)` on the working set in response to either (a) a `signalEnumerator(for: .workingSet)` from us, or (b) push notifications when configured, or (c) at system-determined intervals (the system, not us, owns the cadence). Our existing `S3Enumerator.enumerateChanges` already implements the contract via `SyncEngine.reconcile`.

**What we DON'T need to build:** a periodic reconciliation timer specifically for thumbnails. The existing `pollingTask` in `FileProviderExtension+Lifecycle` (line 200) is already the only timer we need, and its sole job is to call `signalChanges()` — that's correct and does not have to die.

### 3. Materialization tracking `[CITED: header doc — "The extension may know whether an item is in that set by checking whether its parentItemIdentifier is listed in the materialized containers."]`

The framework tracks which items are materialized on disk and exposes the data via `enumeratorForMaterializedItems()`. We already use this in `FileProviderExtension+Lifecycle.collectMaterializedKeys`. **We do not need our own "is-on-disk" tracking** for thumbnail purposes.

### 4. Thumbnail caching, keyed on `itemVersion.contentVersion` `[CITED: header doc — "This property is used to invalidate the thumbnail cache maintained by the system."]`

The system caches thumbnails internally. The cache is keyed by `NSFileProviderItem.itemVersion.contentVersion`. When `contentVersion` changes between two enumerations of the same item identifier, the system evicts its cached thumbnail and calls `fetchThumbnails(for:)` again on next display. `[CITED: developer.apple.com/forums/thread/731054 — Apple engineer: "thumbnail cache is based on the version of the file ... itemContentVersion for File Provider items"]`

**Implication:** to tell Apple "I just generated a thumbnail for this item — re-fetch it," we either:
1. Bump `contentVersion` for the item in the next `enumerateItems` / `enumerateChanges` response and call `signalEnumerator(for:)` for the parent container; OR
2. Rely on the natural eviction the next time the file's source ETag changes.

For our use case — generating a thumbnail for an unchanged source file — option (1) is the right primitive. Strategy: encode the **thumbnail availability** into `contentVersion` (e.g., `Data(sourceETag + ":" + thumbStatus)`) so when a thumbnail flips from absent → present, `contentVersion` changes and the system re-requests.

**What we DON'T need to build:** our own thumbnail cache, our own re-request timer, our own "thumbnail freshness" tracking outside of `contentVersion`.

### 5. NO per-item `signalChange` API `[CITED: header inspection — only `signalEnumerator(for: containerItemIdentifier)` exists]`

The framework only has container-level signaling. We signal the parent container of an item, and the system re-enumerates the container, picks up the new `contentVersion`, and re-fetches the thumbnail.

**What we DON'T need to build:** a per-item invalidation queue. We just call `signalEnumerator(for: parentContainer)` once per drive root after a thumbnail upload — coarse-grained, low-cost, and exactly what the API offers.

### 6. Apple's reference sample `FileProviderTrial` does NOT do background indexing `[CITED: github.com/seanses/FileProviderTrial — verified no `BFS`, no pass loops, no coordinator types]`

The reference sample uses `DistributedNotificationCenter` to receive change notifications and signals enumeration in response. **It implements `fetchThumbnails` not at all** (so cannot be used as a positive thumbnail reference) — but the absence of a background indexer in Apple's own canonical pattern is itself the strongest possible signal that we should not be running one either.

## Recommended architecture

### Sequence: cold-folder browse (the cold-folder UX bug, fixed)

```
User navigates to /Photos/2024/ in Finder
    ↓
Apple FP → FileProviderExtension.enumerator(for:) → S3Enumerator (already exists)
    ↓
S3Enumerator.enumerateItems → S3Lib.listS3Items (S3-first, parallel-friendly)
    ↓
items returned, badged, displayed in Finder ← USER SEES FOLDER CONTENTS NOW
    ↓
Apple FP iterates visible items, calls fetchThumbnails(for: [items]) for raster ones
    ↓
For each item:
    fetchThumbnails consume-path:
        cache hit (.thumbnails/<key>.jpg in S3)? → bytes returned, done.
        cache miss?
            ↓
            acquire ThumbnailFallbackLimiter slot (2 permits)
            ↓
            download original via existing s3Lib.downloadS3Item (already in fetchContents path)
            ↓
            ThumbnailRenderer.renderJPEG(from: tempURL) → JPEG bytes
            ↓
            return bytes via perThumbnailCompletionHandler ← USER SEES THUMBNAIL NOW
            ↓
            Task.detached:
                s3Client.putThumbnail(...) → .thumbnails/<key>.jpg now in S3
                signalEnumerator(for: parentContainerOf(item))
                ↓
                Apple FP re-enumerates folder, S3Item.itemVersion.contentVersion bumped
                ↓ (next time user re-opens folder OR Apple re-checks)
                Apple invalidates its thumbnail cache, calls fetchThumbnails again
                ↓
                cache HIT this time. No more fallback cost for this item ever.
```

### Sequence: external change reconciliation (no custom code path)

```
Another device uploads /Photos/2024/new.jpg → S3
    ↓
(no push) → 30s pollingTask fires signalEnumerator(for: .workingSet)
    ↓
Apple FP → S3Enumerator.enumerateChanges → SyncEngine.reconcile (already exists)
    ↓
reconcile diff returns new key, Apple FP discovers the new item
    ↓
when user navigates near it: enumerateItems serves it (already exists)
    ↓
when user's folder view shows it: fetchThumbnails fires (Apple FP iterates visible)
    ↓
... same cold-folder flow as above
```

**Note:** No code we control runs "between" the upload on another device and our discovery. The system + our existing `pollingTask` + our existing `enumerateChanges` handles it.

### Sequence: upload-time thumbnail (unchanged from Phase 13)

```
User drops image into Finder folder
    ↓
Apple FP → FileProviderExtension.createItem → s3Lib upload, returns success ← USER SEES FILE
    ↓
post-PUT fire-and-forget Task:
    isRasterExtension(filename)? → no: done.
    ↓ yes
    ThumbnailUploader.generateAndUpload (Phase 13 already correct)
        render → put .thumbnails/<key>.jpg
        ↓
        signalEnumerator(for: parentContainer) ← TRIGGERS APPLE TO RE-FETCH thumbnail
```

### Sequence: cascade (unchanged from Phase 13)

```
User deletes image → FileProviderExtension.deleteItem → S3 delete OK ← USER SEES DELETION
    ↓
fire-and-forget: deleteThumbnail(.thumbnails/<key>.jpg)
```

### Sequence: pause / resume

Pause is a per-handler check (`SharedData.isDrivePaused`). With no BFS, there's nothing to "halt" — `fetchThumbnails`, `fetchContents`, `enumerateItems`, and the upload hook all already check and short-circuit. **THUMB-21 trivially satisfied.**

## Anti-patterns rejected

| Pattern | Why rejected |
|---|---|
| **Background timer to scan for missing thumbnails** | Apple already drives `enumerateItems` + `fetchThumbnails` reactively. A scanner runs in addition to the framework, never instead of it — pure overhead. |
| **"Eager prefetch of immediate children when folder opens"** | Folder open already triggers `enumerateItems` which the framework already pages. Prefetching children before the user navigates wastes bandwidth on folders the user never enters. |
| **Tray "indexing" state machine** | With no global pass, "indexing" has no global state. Per-folder transient indexing pulses already collapse to "busy" via `NotificationManager`'s existing aggregator. |
| **Custom prefix prioritization queue** (`BreadthFirstIndexer.prioritize`) | The user-visible folder open triggers `enumerateItems` with the right prefix immediately — no prioritization needed. |
| **"Keep BFS as defense in depth"** | Two systems doing the same job is twice the bug surface. The audit findings (Findings 4, 5) are direct consequences of BFS racing the consume + cascade paths. Removing BFS removes the race entirely. |
| **Periodic orphan sweep** | Cascades are the sole prevention. Orphans waste S3 storage, never cause data loss. The 50-orphans-per-pass cap exists precisely because we don't trust the sweep — drop the sweep instead. |
| **Schema V4 `thumbnailFailCount` field** | Per-item failure count survives only as long as the extension process. Resetting on extension restart is acceptable. Schema migrations are cheap to add but expensive to maintain. |
| **`MetadataStore.thumbnailStatus` field** | The "is this thumbnail uploaded?" question is answered by S3 itself — `getThumbnailBytes` returns bytes or nil. SwiftData mirroring of S3 state was useful only for `fetchPendingThumbnails`; with no batch coordinator, no consumer remains. |
| **Cache warm-up on launch** (`warmCacheThenStartBFS`) | Recursive listing burns 1-30s of launch time + bandwidth, and the resulting `MetadataStore` populate is overwritten by per-folder `enumerateItems` on first navigation anyway. Sentinel purge logic is the only useful piece — extract that. |
| **`runThumbnailRolloutIfNeeded` launch-time iteration** | Phase 11 wizard already runs `inspectThumbnailPrefix` at drive-add. Re-running on every launch buys ~nothing for the cost of N ListObjectsV2 calls + persistence churn. |

## Migration plan

### Removal order (build stays green between commits)

This is research, not planning, but the planner needs to know the order is feasible. Recommended sequence:

1. **Add `ThumbnailFallbackLimiter` + extend `fetchThumbnails` cache-miss fork** (additive, no removals yet) → build green, manual smoke shows fallback path works.
2. **Add `signalEnumerator(for: parentContainer)` call after upload-hook PUT** (additive) → build green, smoke shows post-upload thumbnails appear without manual refresh.
3. **Encode thumb-availability into `S3Item.itemVersion.contentVersion`** (additive) → build green, smoke shows Apple re-fetches thumbnails after async PUT completes.
4. **Delete `BFSThumbnailHookRunner` + the `runThumbnailPassTailHooks` callout in `BreadthFirstIndexer`** → BFS still runs (cache-warming-only), but no thumbnail pass-tail. Build green.
5. **Delete `ThumbnailBackfillCoordinator`** (no callers after step 4) → build green.
6. **Delete `OrphanSweeper`** (no callers after step 4) → build green.
7. **Delete `BreadthFirstIndexer` + `QueueManager` + `prioritize(prefix:)` callsite** → build green; user-visible behavior unchanged because `enumerateItems` already does the same work reactively.
8. **Delete `warmCacheThenStartBFS`** (extract sentinel-purge into separate `purgeSentinelsIfNeeded` one-shot) → build green.
9. **Delete Schema V4 `thumbnailFailCount` field** (lightweight migration backward — additive-field-removal works under SwiftData with custom migration; OR ship as Schema V5 add-back-removed if simpler) → build green. **Defer to planner.**

## Open questions for discuss-phase

1. **Schema V4 / V5 field removal.** Removing a SwiftData property after it has been added in production is more delicate than adding one. The "cleanest" path is to ship Schema V6 that drops the field via a migration. The "lazy" path is to leave the field in the schema, never read or write it, and let it die in a future cleanup. Recommend the lazy path for ship velocity; the planner can opt for the cleanest path if disk hygiene matters.
2. **`runThumbnailRolloutIfNeeded` lifecycle.** Survive or die? It does drive-iteration at launch, which conflicts with "no work at launch" but is independent of BFS. Recommend dropping per the same anti-pattern principle, but it's not a pure thumbnail concern. **User decision.**
3. **`warmCacheThenStartBFS` sentinel-purge logic.** Survive or die? It's defensive cleanup for a pre-fix bug. Probably one-shot done; can drop entirely. Recommend dropping.
4. **Tray status reduction.** {idle, busy, error, paused} or {idle, error}? `S3Enumerator` produces transient indexing pulses on every folder open. If we want "show busy when actively listing," keep busy. If we want "show error or nothing," drop busy. Recommend keeping busy as the most user-meaningful signal.
5. **`contentVersion` derivation strategy.** Two options for encoding thumb-availability:
   - (a) `contentVersion = sha256(sourceETag + thumbAvailableBit)` — requires an in-memory `[String: Bool]` cache populated by consume-path successes.
   - (b) `contentVersion = sha256(sourceETag + lastModifiedOfThumbInS3 ?? "none")` — adds a HEAD request per item (rejected: too costly).
   - Recommend (a). The cache lives in `ThumbnailFallbackLimiter` alongside the strike counter.
6. **Memory pressure of the new fallback path.** Hybrid path downloads the full original to a temp file (could be 30-50 MB for a HEIC photo) then renders. macOS extension memory ceiling is ~50 MB safe. Concurrency=2 means 2 simultaneous full-image-mapped renders; pathological case is two 50 MB images. `Data(contentsOf: .mappedIfSafe)` mmap-friendly per Finding 2 fix; should stay under budget. Worth profiling once during planning. **Planner action: include a memory smoke test in the integration suite.**
7. **Pre-13 user-experience regression for "old" S3 buckets with no thumbnails yet.** Today: user opens cold folder, waits 5-30 min for BFS to chew through the bucket. With reshape: user opens cold folder, sees thumbnails appear over 5-10 seconds (per-item fallback render). For a 1000-image folder, total bandwidth is ~3-5 GB on first visit, ~50 MB on subsequent visits. **Acceptable per Finding 7 D-7.1 + D-7.4 — "bandwidth cost is amortized per item, not per folder-open."** Still worth a discuss-phase confirmation.
8. **Does `enumerateChanges` on the working set still need `SyncEngine.reconcile`?** The reconcile is heavy (full recursive S3 listing). Could be replaced by a lighter "list-only-since-anchor" path. **Out of scope for 13.2 — flagged for a later phase.**
