    **Step E — `cancelInFlight()` API:**

    ```swift
    public func cancelInFlight() {

    }
    ```

    To make this work, `runBatch` must wrap the loop body in a tracked Task. One clean shape: when `runBatch` is invoked, it sets `currentTask = Task { try await self.processLoop(...) }` and `await currentTask?.value`; alternatively, since `runBatch` itself runs on the actor's task, callers need a mechanism. The cleanest implementation:

    Actor methods inherit cancellation from the Task that invoked them. So if `BFSIndexer` does:
    ```swift
    let task = Task { try? await coordinator.runBatch(maxItems: 5) }
    self.currentBackfillTask = task
    // later: self.currentBackfillTask?.cancel()
    ```
    the cancellation propagates into runBatch's actor execution — `try Task.checkCancellation()` inside runBatch will throw.

    Therefore: **`cancelInFlight()` on the coordinator is OPTIONAL syntactic sugar.** Plan 13-09 will store the Task externally in the BFS indexer. The simpler design: do NOT add `cancelInFlight()` to the coordinator. Instead, the coordinator just trusts incoming Task cancellation. Document this in a docstring:

    ```swift
    /// Cancellation: the caller is responsible for storing the Task that invoked runBatch
    /// and calling .cancel() on it (e.g., when the drive is paused). This actor cooperates
    /// by calling try Task.checkCancellation() between phases.
    ```
