## A1 — `flat_error` shape of `Ds3Error`

**Verdict: needs-fix (cosmetic; Plan 02 should add `ds3_error_code` free function).**

The Rust enum has `#[uniffi(flat_error)]` (error.rs:10), so UniFFI emits ONE Swift enum with the variant names preserved, but every variant carries only a single `(message: String)` payload regardless of the Rust-side fields:

```swift
// From DS3CoreFFI.swift:2110-2208 (verified)
public enum Ds3Error: Swift.Error, Equatable, Hashable, Foundation.LocalizedError {
    case InvalidUrl(message: String)
    case ServerError(message: String)        // Rust had { status: u16, body: String } — LOST
    case JsonError(message: String)
    case Encoding(message: String)
    case LoggedOut(message: String)
    case TokenExpired(message: String)
    case Missing2Fa(message: String)         // <-- 2FA case (D-15 load-bearing)
    case CookieError(message: String)
    case MissingUploadId(message: String)
    case EmptyFileData(message: String)
    case MissingETag(message: String)
    case ParseError(message: String)
    case UnableToOpenFile(message: String)
    case IoError(message: String)
    case HttpError(message: String)
    case S3Error(message: String)            // Rust had `S3Error(String)` — body collapsed to message
    case AuthError(message: String)

    public var errorDescription: String? { String(reflecting: self) }
}
extension Ds3Error: Sendable {}              // emitted at line 2212
```

### Implication for downstream plans

- **Plan 02 (S3 adapter) — Two viable patterns:**
  1. **Switch on case directly:** Swift can pattern-match each variant by name without a numeric code (`case .Missing2Fa, case .S3Error(let msg) where msg.contains("NoSuchKey")`). This works today, no Rust changes needed for the simple cases.
  2. **Expose `ds3_error_code` UniFFI free function** (recommended by RESEARCH §Pitfall 1) to dispatch on integers 1001-3004. This is the cleaner translator code from PATTERNS.md §"Pattern 3: Per-Adapter Error Translation". `code()` method already exists at error.rs:97-117.

- **Plan 02 MUST add `ds3_error_code`** as a `#[uniffi::export]` free function in `core/ds3-ffi/src/uniffi_exports.rs` to keep the per-adapter translator tables readable. Pattern: copy `conflict_key` declaration (Plan 02 Task signature: add a small `pub fn ds3_error_code(err: &DS3Error) -> i32 { err.code() }`). UniFFI flat_error allows borrowing the error by reference in free fns — verify during Plan 02.

- **Server-error response body parsing (`ServerError { status, body }`):** since the Rust `body` field is collapsed into the message string, the Swift adapter cannot extract HTTP body for diagnostic logging without parsing the formatted message (`"Server error: HTTP 401"`). If retaining `body` matters, Plan 02 should consider removing `#[uniffi(flat_error)]` and porting to a full UniFFI Error mirror. **Decision deferred to Plan 02 author.**

### 2FA preservation (D-15)

`Ds3Error::Missing2Fa` maps cleanly: Swift adapter writes
```swift
} catch Ds3Error.Missing2Fa {
    throw DS3AuthenticationError.missing2FA
}
```
No code or message parsing needed for this critical case. LoginViewModel path stays byte-identical.

## A2 — aws-sdk-s3 retry behavior

**Verdict: verified for S3, needs-fix for reqwest.**

### S3 layer (verified at `core/ds3-s3/src/client.rs:51-71`)

```rust
let config = aws_sdk_s3::config::Builder::new()
    .behavior_version_latest()
    .endpoint_url(endpoint)
    .credentials_provider(creds)
    .region(Region::new(region.unwrap_or("us-east-1").to_string()))
    .force_path_style(true)
    .build();
```

`.behavior_version_latest()` is set. Per `aws-sdk-s3` 1.x docs, this enables the SDK's default retry strategy (`StandardRetryPartition`) with `max_attempts(3)`, exponential backoff with jitter, on transient HTTP failures, 5xx, 429 (`SlowDown`), and connection resets. **No Plan 02 retry wiring needed for S3 ops.**

**HOWEVER:** the `MAX_RETRIES` constant declared at client.rs:29 (`pub const MAX_RETRIES: u32 = 5;`) is NOT applied to a `RetryConfig`. It is dead code at present. If Phase 16 desires 5 retries (vs the SDK default 3), Plan 02 should add:
```rust
.retry_config(RetryConfig::standard().with_max_attempts(MAX_RETRIES))
```
to the builder chain. **Recommendation:** add it; this matches the original Soto/Swift `DefaultSettings.S3.maxRetries` expectation.

### HTTP layer (verified at `core/ds3-http/src/client.rs:21-35`)

`SharedHttpClient` uses raw `reqwest::ClientBuilder` with NO retry middleware. Auth, projects, keys, and forge HTTP calls do NOT retry. This is a divergence from the Apple-side Soto behavior (Soto handled 5xx retries automatically).

### Implication for downstream plans

- **Plan 02 / 03 (Rust additions, optional):** wire `reqwest-retry` + `reqwest-middleware` into `core/ds3-http/src/client.rs` (RESEARCH §"Code Examples — reqwest retry policy" lines 684-696). Two new workspace deps.
- **Alternatively, accept current behavior** and document that auth flows have no client-side retry (the Cubbit IAM service is typically stable). Match Phase 16 budget against this scope item.
- **For Phase 16 Plan 01 specifically, no action needed.**

- **No Swift extension code needs to be added in Plan 01's smoke test.**

## Newly Observed Risks (not in original assumptions)

### R-01: Build script overwrites `DS3CoreFFI.swift` with `ds3_models.swift`

**Severity: HIGH (would block Plan 02-07 entirely).**

`core/scripts/build-xcframework.sh` step 6 (lines 137-144) loops over `${OUT_DIR}/*.swift`, picks the first non-`DS3CoreFFI.swift` file, and copies it to `${OUT_DIR}/DS3CoreFFI.swift`. Because `ds3_models.swift` sorts before `DS3CoreFFI.swift` alphabetically and uniffi-bindgen already emits both files alongside each other, the script CLOBBERS the freshly-generated `DS3CoreFFI.swift` (the one containing `Ds3SessionHandle` and FFI methods) with the `ds3_models.swift` content.

**Evidence:** `wc -l` on the fresh bindgen output: `ds3_models.swift = 2591 lines`, `DS3CoreFFI.swift = 1467 lines`. After the script's step 6, the on-disk `DS3CoreFFI.swift` is 2591 lines — i.e. it's `ds3_models.swift` content. `grep "DS3SessionHandle"` against post-script output returns 0 hits.

**Fix applied in Plan 01 Task 2** (Rule 1 deviation): the build script needs to either (a) skip the step 6 copy entirely (since uniffi-bindgen already emits properly-named files), or (b) ensure both Swift files (`ds3_models.swift` AND `DS3CoreFFI.swift`) are preserved and added to the SPM target. The simplest fix: **delete step 6 entirely** and instead let the SPM target consume BOTH `DS3CoreFFI.swift` + `ds3_models.swift` as source files alongside the binary target. This is the canonical UniFFI multi-module pattern.

### R-02: Two UniFFI scaffolding calls produce two Swift modules

Both `ds3-ffi/src/lib.rs:11` and `ds3-models/src/lib.rs:11` call `uniffi::setup_scaffolding!()`. This means uniffi-bindgen emits TWO Swift binding files (`DS3CoreFFI.swift` for `ds3-ffi` symbols, `ds3_models.swift` for `ds3-models` types), TWO `.h` headers, and TWO `.modulemap` files. The build script's step 3 already copies both modulemaps and headers to `Headers/`, but step 6 only handles one Swift file.

**Implication for Plan 01 Task 2:** The SPM `.binaryTarget` provides the linker contract for the C-ABI shared library. The Swift bindings (`DS3CoreFFI.swift` + `ds3_models.swift`) must be **bundled as Swift source files into the DS3Lib target** (or a sibling target). Plan 01 Task 2 must:

1. Copy both Swift files into `apple/DS3Lib/Sources/DS3CoreFFI/` (or similar) and declare a `.target(name: "DS3CoreFFI", dependencies: [.target(name: "DS3CoreFFIRust")])`-style structure, where `DS3CoreFFIRust` is the binary target supplying the `.a` libs.
2. **OR** have the Run Script Phase copy these `.swift` files into the build's intermediates and add them to Compile Sources. The latter is non-trivial in `project.pbxproj`.

**Decision:** Plan 01 Task 2 will go with approach (1). The build script will be modified to write `DS3CoreFFI.swift` + `ds3_models.swift` into `apple/DS3Lib/Sources/DS3CoreFFI/` and declare a sibling SPM target that wraps both the binary lib and the Swift glue. **Plan 02/03 references to `import DS3CoreFFI` then resolve correctly.**

### R-03: Module name collision (`DS3CoreFFI` binary vs `DS3CoreFFI` Swift module)

If a Swift target named `DS3CoreFFI` exists alongside a binary target also named `DS3CoreFFI`, SPM rejects the manifest. Resolution (Task 2): the binary target is renamed `DS3CoreFFIRust` (internal), and the public-facing Swift wrapper target is named `DS3CoreFFI`. Consumers `import DS3CoreFFI`. Pattern parallels canonical Mozilla UniFFI XCFramework setups.
