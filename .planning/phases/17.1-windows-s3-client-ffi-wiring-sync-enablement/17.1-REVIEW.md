# Phase 17.1: Code Review Report (UAT-hardening commits)

**Reviewed:** 2026-06-02
**Depth:** deep
**Scope:** `580ae9b..HEAD` — 5 commits (FFI last-error channel, progress decoupling, byte-range hydration, UAT fixes, roadmap). NOTE: this file overwrites the earlier standard-depth review of the already-merged phase commits; it covers ONLY the 5 UAT-hardening commits in range.
**Status:** issues_found

## Narrative Findings (AI reviewer)

### Summary

This change set wires the Windows cfapi hydration path to real S3 downloads, adds a per-key
download-dedupe with a refcounted temp-file lifecycle, switches to on-demand/eager placeholder
population, adds a thread-local FFI last-error diagnostic channel, and a "stay logged in"
session-restore path.

The transfer.rs progress-throttle and the FFI last-error channel are correct (verified: the first
chunk always reports via `unwrap_or(true)`, a final 100% always fires; `set_last_error` runs on
the calling C# thread synchronously with `Check`, so no thread-local race; the empty-string free
path is a ZST allocation, not a leak). The poll-level diff is level-consistent
(`ListByPrefixAsync` filters by `parent_key`, matching the delimited remote listing).

However the byte-range hydration path and the cfapi provider teardown contain real correctness and
concurrency defects. The most serious are: (1) a temp-file sharing/case-collision corruption risk
in the shared-download refcount; (2) `CfApiProvider.DisposeAsync` disposing the fetch semaphore and
disconnecting the sync root while fire-and-forget fetch/populate tasks are still in flight; and
(3) a path-prefix boundary bug in `RelativeKeyFromFullPath` that can derive the wrong S3 key and
mis-route deletes/renames.

## Critical Issues

### CR-01: Shared-download dedupe: case-insensitive key collision + non-delete-tolerant FileStream → corruption / leaked temp files

**File:** `windows/DS3Drive.Sync/CfApi/FetchDataHandler.cs:59-60, 174-195, 235-298`

**Issue:** Two distinct defects in the dedupe/temp-file lifecycle:

1. **Case-insensitive key map over case-sensitive S3 keys.** `_downloads` uses
   `StringComparer.OrdinalIgnoreCase` (line 60). S3 object keys are case-sensitive: `Report.pdf`
   and `report.pdf` are different objects. Two concurrent FETCH_DATA callbacks for those keys
   collide onto a single `SharedDownload`, so the second callback serves byte ranges out of the
   *first object's* temp file → **silent data corruption** (wrong bytes hydrated into the
   placeholder). The cfapi NormalizedPath preserves case, so this is reachable from normal use.

2. **`FileStream` opened without `FileShare.Delete`.** `StreamRangeAsync` opens the temp with
   `FileShare.Read` (line 239). If the last releaser reaches RefCount 0 and calls
   `TryDelete(temp)` while another callback still holds the read handle (a legitimate refcount
   interleave: A joins, A serves+releases to 1, B was already serving but a third releaser drops
   to 0), the delete throws a sharing violation, is swallowed, and the temp file leaks. Over a
   busy session this leaks `%TEMP%\ds3fetch_*` unboundedly.

**Fix:**
```csharp
// 1. case-sensitive map — S3 keys are case-sensitive
private readonly ConcurrentDictionary<string, SharedDownload> _downloads =
    new(StringComparer.Ordinal);

// 2. tolerate concurrent delete while a read is in flight
await using var fs = new FileStream(
    tempPath, FileMode.Open, FileAccess.Read,
    FileShare.Read | FileShare.Delete, ChunkSize, useAsync: true);
```
Also wrap `TryDelete` to retry on `IOException`, or open the temp with `FileOptions.DeleteOnClose`
semantics tied to the last handle.

### CR-02: `CfApiProvider.DisposeAsync` tears down resources while fetch/populate tasks are in flight

**File:** `windows/DS3Drive.Sync/CfApi/CfApiProvider.cs:107, 148-175`

**Issue:** Dispose races against fire-and-forget work:
- `PopulatePlaceholdersAsync(ct)` is launched with `_ = Task.Run(..., ct)` (line 107) using the
  *RegisterAsync caller's* token, never cancelled by `DisposeAsync`. On dispose this task can call
  `CfCreatePlaceholders` *after* `CfDisconnectSyncRoot(_connectionKey)` (line 161).
- Every `OnFetchData` / `OnFetchPlaceholders` spawns an untracked `Task.Run(...)`. `DisposeAsync`
  calls `_fetchSemaphore.Dispose()` (line 172) with no drain. An in-flight `StartDownloadAsync`
  then hits `_fetchSemaphore.WaitAsync()`/`.Release()` on a disposed semaphore →
  `ObjectDisposedException`, and the handler keeps calling `AckTransfer` / `CfReportProviderProgress`
  against a connection key that `CfDisconnectSyncRoot` already invalidated — undefined behavior at
  the native boundary.
- `CfDisconnectSyncRoot` is issued while callbacks may still be mid-`CfExecute` on `_connectionKey`.

**Fix:** Add a shutdown CTS linked to the populate task; gate new callbacks on `_disposed`; drain
in-flight handler tasks before disposing the semaphore; disconnect the sync root only after quiesce:
```csharp
private readonly CancellationTokenSource _shutdownCts = new();
// RegisterAsync: _ = Task.Run(() => PopulatePlaceholdersAsync(_shutdownCts.Token), _shutdownCts.Token);

public async ValueTask DisposeAsync()
{
    if (_disposed) return;
    _disposed = true;
    _shutdownCts.Cancel();
    // await in-flight HandleAsync tasks (track them) with a bounded timeout, THEN:
    if (_connected) { try { CfDisconnectSyncRoot(_connectionKey).ThrowIfFailed(); } catch (Exception ex) { _logger.LogWarning(ex, "..."); } _connected = false; }
    await _uploads.DisposeAsync().ConfigureAwait(false);
    _fetchSemaphore.Dispose();
    _shutdownCts.Dispose();
}
```

### CR-03: `RelativeKeyFromFullPath` strips the sync root with an unbounded `StartsWith` → wrong S3 key, mis-routed delete/rename

**File:** `windows/DS3Drive.Sync/CfApi/PathValidation.cs:155-180`

**Issue:** The sync-root prefix is stripped via `normalized.StartsWith(rootRelative, OrdinalIgnoreCase)`
+ `normalized[rootRelative.Length..]`, with no check that the match ends on a `/` boundary. A
sibling path sharing a name prefix collides. With sync root volume-relative
`Users/me/Cubbit/drive` and a path `Users/me/Cubbit/drive-backup/file.txt`, `StartsWith` is true
and stripping yields `-backup/file.txt`, which flows into the S3 key. Because this feeds
`NotifyDeleteHandler` and `NotifyRenameHandler` (both now `S3KeyFromFullPath`), a delete/rename can
hit the **wrong S3 object** — silent remote data corruption on a path collision.
`TryValidateS3Key` does not catch it (`-backup/file.txt` is a valid key).

**Fix:** Require a separator boundary after the matched root (and reject paths not under the root
rather than silently treating them as relative):
```csharp
if (rootRelative.Length > 0 &&
    normalized.StartsWith(rootRelative, StringComparison.OrdinalIgnoreCase) &&
    (normalized.Length == rootRelative.Length || normalized[rootRelative.Length] == '/'))
{
    normalized = normalized[rootRelative.Length..].TrimStart('/');
}
```

## Warnings

### WR-01: `NotifyFileCloseHandler` validates the relative key but uploads the full key — inconsistent trust boundary

**File:** `windows/DS3Drive.Sync/CfApi/NotifyFileCloseHandler.cs:54-79`
**Issue:** It runs `TryValidateS3Key(relativeKey, ...)` but uploads `s3Key = (prefix ?? "") + relativeKey`
and never re-validates the prefixed key. Every other handler in this change validates the *full*
`S3KeyFromFullPath` result. A malformed drive prefix would be rejected by the others but accepted
here, and the upload job + `ResolveLocalPath` mix relative/full keying.
**Fix:** Validate the same `s3Key` that is uploaded, mirroring fetch/rename/delete; derive the
local path from one consistent key.

### WR-02: Shared download reports progress against only the *first* caller's transfer key — joiners can starve the watchdog

**File:** `windows/DS3Drive.Sync/CfApi/FetchDataHandler.cs:202-219`
**Issue:** `StartDownloadAsync` reports `CfReportProviderProgress` against the
connection/transfer key of whichever callback started the download. If that first transfer is
cancelled (Win32 398) while later joiners await `entry.PathTask`, the watchdog resets go to a dead
key and the live joiners get no motion during a long download → they can hit the 60s deadline and
be cancelled — reintroducing the retry-forever symptom the dedupe was meant to fix.
**Fix:** Heartbeat `CfReportProviderProgress` per-waiter (each `HandleAsync` against its own
transfer key while awaiting `PathTask`), rather than reporting only the originator's key.

### WR-03: A faulted shared download fails all joiners together and is cached until the last release

**File:** `windows/DS3Drive.Sync/CfApi/FetchDataHandler.cs:121-147, 166`
**Issue:** If `StartDownloadAsync` throws, `entry.PathTask` is faulted; every concurrent
`await entry.PathTask` rethrows it, so one transient S3/network error fails *all* in-flight
callbacks for that key at once. The faulted task stays cached until the last joiner releases, so a
mid-window joiner inherits the fault instead of retrying.
**Fix:** Under lock, on failure reset `entry.PathTask = null` so a subsequent joiner restarts the
download; document the fail-fast-for-current-joiners behavior.

### WR-04: `PersistSession` does an FFI hop + Credential Manager write on every IAM-token forge (browse hot path)

**File:** `windows/DS3Drive.App/Services/AuthenticationService.cs:357-361`,
`windows/DS3Drive.ViewModels/Services/DS3SdkService.cs:223`
**Issue:** `IDS3SessionGateway.ForgeIamToken` now persists after every forge, and browse forges per
`(project, IAM user)` on every bucket listing / picker switch. Each persist calls
`CurrentRefreshToken()` (FFI) + a synchronous Credential Manager `Save`. Repeated picker switches
hammer the secure store with unbounded write amplification and add latency to browsing.
**Fix:** Persist only when the refresh token actually changed (compare to last-persisted), or skip
persistence on the forge-for-browse path — login + token-refresh already cover rotation.

### WR-05: `restore_from_refresh_token` does not validate the rotated token is non-empty before persisting

**File:** `core/ds3-auth/src/session.rs:101-138`
**Issue:** The seed `AccountSession` carries `token: ""` / `exp: 0` and relies entirely on the
`_refresh` cookie. There is no check that `new_token.token` / `new_refresh` are non-empty after the
exchange; a server returning an empty rotated refresh token would be persisted and brick the next
restore. The empty seed also couples tightly to `refresh::refresh_token` never reading
`seed.token`.
**Fix:** After the exchange, return `DS3Error::AuthError` if `new_token.token` or `new_refresh` is
empty, so a malformed response fails loudly to the login fallback instead of persisting garbage.

### WR-06: `App.IsShuttingDown` static + `_window`-captured restore continuation are process-global / lifetime-fragile

**File:** `windows/DS3Drive.App/App.xaml.cs:232-258, 318-405`,
`windows/DS3Drive.App/MainWindow.xaml.cs:34-41`
**Issue:** `IsShuttingDown` is a static read by every `MainWindow.OnAppWindowClosing`; the static
closing handler unconditionally cancels-and-hides for any window — a second window would be
un-closable. `RestoreSessionThenRoute` enqueues onto `_window?.DispatcherQueue` from a background
task with no guard that `_window` is alive/not closing; quitting during the restore network call
navigates a window mid-teardown. The `AuthStateChanged` subscription wired at host start (line 240)
is never unsubscribed.
**Fix:** Scope shutdown intent to the window instance (check `sender` identity); guard the
dispatcher continuation against a disposed window; unsubscribe `AuthStateChanged` on shutdown.

### WR-07: `FetchPlaceholdersHandler` failure-completion can itself throw and leave Explorer hung to the watchdog

**File:** `windows/DS3Drive.Sync/CfApi/FetchPlaceholdersHandler.cs:563-606, 613-648`
**Issue:** On the error path, `HandleAsync` calls `TransferPlaceholders(..., StatusUnsuccessful)` to
unstick Explorer, but `TransferPlaceholders` catches and swallows a throwing `CfExecute`. If the
*success*-status `CfExecute` partially ran or the failure-status call throws, the transfer is never
completed and Explorer hangs on the directory until the 30s watchdog — the exact symptom the error
branch exists to avoid.
**Fix:** Ensure exactly one completion is attempted and guaranteed; separate "transfer
placeholders" from "complete with failure status" so a throw in the former still drives a
completion ack.
