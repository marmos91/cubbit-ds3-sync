# Phase 17.1: Code Review Report

**Reviewed:** 2026-06-01
**Depth:** standard
**Files Reviewed:** 17
**Status:** issues_found

## Summary

This phase re-homes the S3 surface from `DS3Session` onto a per-drive `DS3DriveS3Client`
that owns a real `ds3_s3_client_new` handle, and wires it through the sync host
(`SyncHostedService`) and the wizard browse path (`DS3SdkService`). The handle-lifecycle
mechanics are mostly sound: `Interlocked.Exchange` single-shot dispose, `EnsureHandle`
short-circuit, `fixed`-pinned UTF-8 marshalling, `GC.KeepAlive` on the progress delegate,
and the Rust `ffi_guard!` panic boundary all match the documented contracts. The P/Invoke
signatures in `DS3Native.cs` line up field-for-field with the Rust `extern "C"` exports.

The defects cluster around two themes: (1) **plaintext-secret retention** — the design
docs repeatedly promise the S3 secret is "NOT retained beyond the `Create` call," but two
code paths hold it for the full drive lifetime, and one writes it into a process-wide
credential record used for equality; (2) **native-handle lifecycle on non-happy paths** —
a use-after-free window in the wizard-browse dispose path that (unlike the sync host) has
no ordering discipline, plus a native-handle leak when drive teardown throws. A `CopyObject`
signature silently discards its destination-bucket argument, a latent data-misplacement trap.

## Critical Issues

### CR-01: Plaintext S3 secret retained for the full drive lifetime, contradicting the documented "not retained" contract

**File:** `windows/DS3Drive.Sync/Hosting/SyncHostedService.cs:38-44`, `windows/DS3Drive.Sync/Hosting/IDriveS3CredentialProvider.cs:9-13`
**Issue:** `ActiveDrive` stores `DriveS3Credentials Creds` (which contains the plaintext
`SecretKey`) for the entire active lifetime of every drive — it lives in the `_active`
dictionary until `StopActiveAsync`. This directly contradicts the contract documented on
the seam: `IDriveS3CredentialProvider.cs:10-12` states the secret "is re-hydrated transiently
from the OS-sealed Credential Manager (T-17.1-09) and is NOT retained beyond the
`DS3DriveS3Client.Create` call," and `DriveS3CredentialProvider`/`DS3SdkService` repeat the
same "not retained C#-side beyond this call (T-17.1-09)" claim. The credential is kept in a
long-lived managed heap object specifically so the rebuild-on-change path can do
`existing.Creds == creds` value-equality — which compares the secret in plaintext on every
`StartDriveAsync` call. This widens the threat surface the phase explicitly set out to close
(plaintext secret in a long-lived, GC-movable, dumpable managed object).
**Fix:** Do not retain the secret for change-detection. Store a non-reversible fingerprint
instead of the live credential, and re-resolve the secret transiently only when a rebuild is
actually needed:
```csharp
private sealed record ActiveDrive(
    CfApiProvider Provider, SyncEngineType Engine, DriveStatusBroadcaster Status,
    CancellationTokenSource Cts, DS3DriveS3Client S3,
    string Endpoint, string AccessKey, string CredsFingerprint); // SHA-256 of endpoint|access|secret

// build fingerprint once, never store SecretKey:
static string Fingerprint(DriveS3Credentials c) =>
    Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes($"{c.Endpoint}\n{c.AccessKey}\n{c.SecretKey}")));
// rebuild check:
if (existing.CredsFingerprint == Fingerprint(creds)) return;
```
Then clear/avoid keeping the `DriveS3Credentials` instance once `DS3DriveS3Client.Create`
returns (it is the only consumer of the live secret).

## Warnings

### WR-01: Use-after-free window in the wizard-browse dispose path — no ordering discipline (unlike the sync host)

**File:** `windows/DS3Drive.ViewModels/Services/DS3SdkService.cs:298-316`, `73-98`
**Issue:** `DS3SdkService` is a DI **singleton** (`App.xaml.cs:128`) whose `Dispose()` runs on
`Host.Dispose()` at shutdown. It frees every cached browse handle
(`client.Dispose()` → `ds3_s3_client_destroy`). But `GetBucketsAsync` and
`ListChildPrefixesAsync` run the S3 call on a background `Task.Run(() => client.ListObjects(...))`.
If such a task is in flight when the app quits, `Dispose()` frees the native client while the
worker thread is mid-`ListObjects` inside Rust → use-after-free / `AccessViolationException` —
the exact failure mode this phase exists to eliminate. The `DS3DriveS3Client` class doc says
ordering "is the host's job (dispose-last)," and the sync host honors that in `StopActiveAsync`;
this browse path has no such guarantee. Additionally, `ListChildPrefixesAsync:84` reads
`_currentBrowseClient` **outside** `_browseLock`, while `GetBrowseClientAsync` mutates it under
the lock — a read of a possibly-disposed reference.
**Fix:** Track in-flight browse operations and drain them before disposing (e.g. a
`CountdownEvent`/`SemaphoreSlim` gate, or a `CancellationTokenSource` cancelled-then-awaited in
`Dispose`), mirroring the host's dispose-last discipline. At minimum, snapshot the client under
`_browseLock` in `ListChildPrefixesAsync`, and make `Dispose` wait for outstanding tasks rather
than freeing handles that may still be on a worker thread.

### WR-02: Native S3-client (and CTS) handle leaks when drive teardown throws

**File:** `windows/DS3Drive.Sync/Hosting/SyncHostedService.cs:209-230`
**Issue:** `StopActiveAsync` runs all teardown steps inside a single `try`, with
`active.S3.Dispose()` as the **last** statement before the `catch`. If any earlier `await`
(`Engine.StopAsync`, `Provider.DisconnectAsync`, `Engine.DisposeAsync`, `Status.ShutdownAsync`)
throws, control jumps to `catch` and both `active.Cts.Dispose()` and `active.S3.Dispose()` are
skipped — leaking the native `DS3S3Client` handle (and the `CancellationTokenSource`) for the
life of the process. During runtime drive churn (remove/re-add, credential rebuilds via
`StartDriveAsync:160-161`) this leaks one native client per failed teardown.
**Fix:** Guarantee the disposes run regardless of earlier failures:
```csharp
try
{
    active.Cts.Cancel();
    await active.Engine.StopAsync(CancellationToken.None).ConfigureAwait(false);
    await active.Provider.DisconnectAsync(CancellationToken.None).ConfigureAwait(false);
    await active.Engine.DisposeAsync().ConfigureAwait(false);
    await active.Status.ShutdownAsync().ConfigureAwait(false);
}
catch (Exception ex) { _logger.LogWarning(ex, "error stopping active drive"); }
finally
{
    active.Cts.Dispose();
    active.S3.Dispose(); // dispose-last, but unconditional
}
```

### WR-03: `CopyObject` silently discards its destination-bucket argument

**File:** `windows/DS3Drive.Core/DS3DriveS3Client.cs:174-186`
**Issue:** `CopyObject(srcBucket, srcKey, dstBucket, dstKey)` does `_ = dstBucket;` and passes
only `srcBucket` into the single-bucket `ds3_copy_object` ABI. If any caller ever passes
`dstBucket != srcBucket`, the copy silently writes to the **source** bucket instead of erroring —
a data-misplacement trap. Current callers (`SyncEngine.cs:221`, `NotifyRenameHandler.cs:69`)
happen to pass the same bucket twice, so it is latent today, but the 4-argument signature
actively invites the cross-bucket call it cannot honor, and the failure mode is silent
(wrong destination) rather than an exception.
**Fix:** Fail loudly until the ABI supports cross-bucket copy:
```csharp
if (!string.Equals(srcBucket, dstBucket, StringComparison.Ordinal))
    throw new NotSupportedException(
        "Cross-bucket copy is not supported by the current ds3_copy_object ABI.");
```
(Or narrow the public signature to a single `bucket` parameter so the trap cannot be expressed.)

### WR-04: `CancellationHandle` parameter accepted then silently dropped on download/upload

**File:** `windows/DS3Drive.Core/DS3DriveS3Client.cs:121-137`, `140-157`
**Issue:** `DownloadObject`/`UploadObject` accept `CancellationHandle? cancel` and discard it
(`_ = cancel;`). The underlying `ds3_download_object`/`ds3_upload_object` exports
(`c_exports.rs:551`, `587`) take **no** cancellation parameter, even though the core exposes a
full cancellation-handle API (`ds3_cancellation_create/cancel/destroy`). Net effect: a caller
that mints a `CancellationHandle` and passes it in reasonably expects an in-progress transfer to
be cancellable; it never will be. This is a silent no-op contract gap (a stuck multi-GB upload
cannot be aborted), and the dropped parameter hides it from callers and reviewers.
**Fix:** Either thread a cancellation token through the FFI (add a `*const CancellationHandle`
param to the download/upload exports and pass it down to `client.download_object`/`upload_object`),
or remove the `cancel` parameter from these C# signatures so the missing capability is visible
at the call site rather than silently accepted.

### WR-05: `DS3AccountInfo` round-trips through the FFI but the in-memory `EndpointGateway` is fragile to a stale `CurrentAccount`

**File:** `windows/DS3Drive.App/Services/DriveS3CredentialProvider.cs:56-64`, `windows/DS3Drive.App/Services/AuthenticationService.cs:189-190`
**Issue:** `DriveS3CredentialProvider` reads `_session.EndpointGateway`, which resolves to
`CurrentAccount?.EndpointGateway` — a value captured **once** at login
(`AuthenticationService.cs:85,94`) and never refreshed. The guard at
`DriveS3CredentialProvider.cs:57` throws only on empty-string. If a token refresh or re-login
ever produced a different account snapshot but `_currentAccount` were not updated (e.g. the
`RefreshToken` path does not re-read account info), drives would mint clients against a stale
endpoint with no detection. The empty-check is necessary but not sufficient.
**Fix:** Either re-read `AccountInfo()` when building credentials, or document/assert that
`endpoint_gateway` is immutable for the account lifetime and add a debug assertion that the
live session's account id still matches `CurrentAccount.AccountId` before using the cached
endpoint.

### WR-06: Reconciliation orphan-key window can leak a live remote API key (and its secret)

**File:** `windows/DS3Drive.ViewModels/Services/DS3SdkService.cs:189-209`
**Issue:** In `LoadOrCreateApiKeyAsync`, the "both present but differ" case (3d) relies on
branches 3b/3c both having fired to delete each side, then falls through to `CreateAndPersistAsync`.
But branch 3b (remote-only delete) only runs when `localApiKey is null`, and 3c (local-only
delete) only when `remoteApiKey is null`. When **both** are non-null but `KeysMatch` is false
(same name, different access key), **neither** delete fires, and the code proceeds straight to
creating a brand-new remote key — leaving the old, mismatched remote key undeleted (an orphan
with live S3 credentials). The comment at 3d claims "both branches above fired," which is
incorrect for the both-present-but-differ case.
**Fix:** Explicitly handle the both-present-but-differ case by deleting the stale remote key
before creating the replacement:
```csharp
if (localApiKey is not null && remoteApiKey is not null && !KeysMatch(localApiKey, remoteApiKey))
{
    await Task.Run(() => _session.DeleteApiKey(user.Id, remoteApiKey.Id, iamToken), ct).ConfigureAwait(false);
    await DeleteLocalApiKeyAsync(apiKeyName, ct).ConfigureAwait(false);
}
```

### WR-07: CI `push` trigger is pinned to a stale phase branch; this phase's branch never runs the gate on push

**File:** `.github/workflows/windows-build.yml:20-27`
**Issue:** The `push` trigger only fires on `gsd/phase-17-windows-shell` and `main`. The active
work branch is `gsd/phase-17.1-windows-s3-client-ffi`, so direct pushes to it do **not** run the
build/test/format gate (only the PR-to-`main` trigger covers it). Given the local dev box "lacks
the MSVC C++ linker" (per the `DS3Native.cs` header) and cannot build the DLL, the CI gate is the
only place the Rust↔C# ABI is actually compiled and the integration harness wiring is validated.
A stale branch filter means the FFI surface in this phase can be pushed repeatedly without the
one environment that can verify it.
**Fix:** Broaden the push filter to cover the phase branch family (e.g. `gsd/phase-17*`) or add
the current branch, so the build/ABI gate runs on push for the branch where the FFI changes live.

## Info

### IN-01: Duplicated `M` marshalling helper class copied across two facades

**File:** `windows/DS3Drive.Core/DS3DriveS3Client.cs:276-307`, `windows/DS3Drive.Core/DS3Session.cs:255-286`
**Issue:** The private `static class M` (Utf8/Len/TakeString/FreeString/WrapProgress) is copied
verbatim into both `DS3DriveS3Client` and `DS3Session` (the comment at line 275 acknowledges the
copy "to keep the diff local"). Any future fix to the marshalling contract (e.g. the `int` cast in
`TakeString` at `len` > `int.MaxValue`) must be applied in two places or they will drift.
**Fix:** Extract a single `internal static class FfiMarshal` in `DS3Drive.Core.Native` and have
both facades use it.

### IN-02: `TakeString` casts `nuint` length to `int` without a bounds check

**File:** `windows/DS3Drive.Core/DS3DriveS3Client.cs:285-295`, `windows/DS3Drive.Core/DS3Session.cs:264-274`
**Issue:** `Encoding.UTF8.GetString((byte*)ptr, (int)len)` casts a `nuint` to `int`. For any FFI
payload ≥ 2 GiB the cast overflows to a negative/wrong length. Out of scope for v1 correctness in
practice (the JSON/string outputs here are small — bucket lists, ETags, presigned URLs), but
`ds3_download_to_memory` is explicitly documented for buffers and a future caller could route a
large payload through a `TakeString`-style helper.
**Fix:** Guard `if (len > int.MaxValue) throw new DS3...;` before the cast, or use the
`ReadOnlySpan<byte>`-with-`nuint` overload where available.

### IN-03: Empty-buffer marshalling sentinel (`EmptyBuf = new byte[1]`) relies on `Len` returning 0

**File:** `windows/DS3Drive.Core/DS3DriveS3Client.cs:278-283`, `windows/DS3Drive.Core/DS3Session.cs:257-262`
**Issue:** `Utf8("")` returns a 1-byte buffer while `Len("")` returns 0, so Rust's
`ffi_opt_str(ptr, 0)` returns `None` and never reads the byte — correct, but the invariant
(pointer non-null yet length 0 ⇒ treated as absent) is load-bearing and undocumented at the
`M` helper. A future change to `Len` (e.g. returning the buffer's `.Length`) would silently feed
a stray `\0` byte across the boundary.
**Fix:** Add a one-line comment on `EmptyBuf`/`Len` asserting the "non-null ptr + 0 len ⇒ None"
contract, or pin `null` for empty strings instead of a sentinel buffer.

### IN-04: Stale/inaccurate doc comment — `IDS3SessionGateway` claims methods mirror `DS3Session` "1:1" but `EndpointGateway`/`AccountId` have no `DS3Session` equivalent

**File:** `windows/DS3Drive.ViewModels/Services/IDS3SessionGateway.cs:10-22`
**Issue:** The interface summary says "Every method mirrors the corresponding `DS3Session` method
1:1," but `AccountId` and `EndpointGateway` are derived from `DS3AccountInfo` (cached on
`AuthenticationService`), not from any `DS3Session` method. Minor doc drift that could mislead a
maintainer into looking for non-existent `DS3Session.EndpointGateway`.
**Fix:** Reword to "the API-key/projects methods mirror `DS3Session` 1:1; `AccountId`/
`EndpointGateway` are sourced from the cached `DS3AccountInfo`."
