## Summary

This is a **handle-plumbing** phase, not a feature phase. The Rust core has a fully-implemented `DS3S3Client` (`core/ds3-s3/src/client.rs:55`) and 15 C-ABI S3 exports that each take a `*const DS3S3Client` first argument — but **no C-ABI export mints one**. The Swift/UniFFI path sidesteps this entirely because UniFFI wraps the S3 client *inside* the session object (`DS3SessionHandle::connect_s3` mutates an internal `RwLock<Option<DS3S3Client>>`, `uniffi_exports.rs:154`). The C# Phase-17 facade copied the *call sites* but had no minting export, so it passed the `DS3Session*` (an `EnsureHandle()` `IntPtr`) into the `*const DS3S3Client` slot. Rust dereferences a `DS3Session` as a `DS3S3Client` → reads garbage → `AccessViolationException` at the wizard's Bucket step.

The fix is two new C-ABI exports (`ds3_s3_client_new` / `ds3_s3_client_destroy`) that `Box`/`Box::from_raw` a `DS3S3Client` exactly like `ds3_authenticate` / `ds3_session_destroy` do for `DS3Session`, plus a new `DS3DriveS3Client : IDisposable` C# facade that owns the resulting handle. The credential source is the existing API-key reconciliation (`DS3SdkService.LoadOrCreateApiKeyAsync`) + the account's `endpoint_gateway`, exactly mirroring macOS `DS3Client.driveS3Client`. The six cfapi sync ops already funnel through one clean seam (`IDS3SessionAccess`), so re-routing them is a localized change to the `AuthenticationService` adapter (or a new adapter) — not a sweep across the engine.

**Primary recommendation:** Add the two exports following the `ds3_authenticate`/`ds3_session_destroy` pattern verbatim (out_handle + out_error for `new`; bare `*mut` drop for `destroy`). Build a `DS3DriveS3Client` that copies the `DS3Session` lifecycle discipline (`Interlocked.Exchange` guard, `EnsureHandle` short-circuit). Mint it from `apiKey.AccessKey` + `apiKey.SecretKey` (re-hydrated from Credential Manager) + `account.endpoint_gateway`, region `None` (defaults to `us-east-1` in the Rust constructor, matching macOS). Re-point both `IDS3SessionGateway.ListBuckets/ListObjects` (wizard) and all of `IDS3SessionAccess` (sync) at the per-drive handle. The `aws_sdk_s3::Client` is `Clone + Send + Sync` and already drives concurrent multipart streams in `ds3-s3`, so the single handle is safe under the `SemaphoreSlim(20,20)`×2 concurrent load.

### Pattern 1: Handle-minting export (mirror `ds3_authenticate`)
**What:** A C-ABI export that constructs a Rust struct, `Box::into_raw`s it into `*out_handle`, and reports errors via `*out_error`.
**When to use:** `ds3_s3_client_new`.
**Example (the pattern to copy — from `c_exports.rs:127`):**
```rust
// Source: core/ds3-ffi/src/c_exports.rs:127 (ds3_authenticate)
#[no_mangle]
pub unsafe extern "C" fn ds3_authenticate(/* …str args… */,
    out_handle: *mut *mut DS3Session, out_error: *mut i32) -> i32 {
    ffi_guard!(out_error, {
        let email = unsafe { ffi_str(email, email_len)? };
        // …
        let session = runtime().block_on(DS3Session::authenticate(/* … */))?;
        unsafe { *out_handle = Box::into_raw(Box::new(session)) };
        Ok::<i32, DS3Error>(0)
    })
}
```
Adapted for S3 (note: `DS3S3Client::new` returns `Self`, NOT `Result`, and does **no** network I/O — so no `runtime().block_on` and the only fallible step is UTF-8 decode):
```rust
#[no_mangle]
pub unsafe extern "C" fn ds3_s3_client_new(
    endpoint: *const u8, endpoint_len: usize,
    access_key: *const u8, access_key_len: usize,
    secret_key: *const u8, secret_key_len: usize,
    region: *const u8, region_len: usize,          // null/0 ⇒ None ⇒ "us-east-1"
    out_handle: *mut *mut DS3S3Client, out_error: *mut i32) -> i32 {
    ffi_guard!(out_error, {
        let endpoint = unsafe { ffi_str(endpoint, endpoint_len)? };
        let access_key = unsafe { ffi_str(access_key, access_key_len)? };
        let secret_key = unsafe { ffi_str(secret_key, secret_key_len)? };
        let region = unsafe { ffi_opt_str(region, region_len)? };   // existing helper
        let client = DS3S3Client::new(endpoint, access_key, secret_key, region);
        unsafe { *out_handle = Box::into_raw(Box::new(client)) };
        Ok::<i32, DS3Error>(0)
    })
}
```

### Pattern 2: Handle-destroy export (mirror `ds3_session_destroy`)
```rust
// Source: core/ds3-ffi/src/c_exports.rs:201 (ds3_session_destroy)
#[no_mangle]
pub unsafe extern "C" fn ds3_s3_client_destroy(handle: *mut DS3S3Client) {
    if !handle.is_null() {
        unsafe { drop(Box::from_raw(handle)) };
    }
}
```
**Marshalling note (`ffi_opt_str` already exists, `c_exports.rs:48`):** a null pointer **or** zero length both decode to `None` → the Rust constructor defaults region to `"us-east-1"`. So the C# side can pass `null, 0` for region with no special-casing — this is the discretionary "region value" call (D discretion): **pass `None`/empty, matching macOS which never sets a region in `DS3S3Client(accessKeyId:secretAccessKey:endpoint:)`.**

### Pattern 3: C# handle-owning facade (mirror `DS3Session` lifecycle)
```csharp
// Mirror of DS3Session.cs:340 Dispose + :351 EnsureHandle
public sealed class DS3DriveS3Client : IDisposable
{
    private IntPtr _handle;
    private DS3DriveS3Client(IntPtr handle) => _handle = handle;

    public static unsafe DS3DriveS3Client Create(string endpoint, string accessKey, string secretKey, string? region = null)
    {
        IntPtr handle; int rc; int err;
        fixed (byte* e = M.Utf8(endpoint), a = M.Utf8(accessKey), s = M.Utf8(secretKey), r = M.Utf8(region))
            rc = DS3Native.ds3_s3_client_new(e, M.Len(endpoint), a, M.Len(accessKey),
                                             s, M.Len(secretKey), r, M.Len(region), out handle, out err);
        if (rc != 0) throw DS3ExceptionFactory.From(err);
        return new DS3DriveS3Client(handle);
    }
    // ListBuckets/ListObjects/HeadObject/Download/Upload/Delete/Copy — copy the
    // bodies from DS3Session.cs:164-268 VERBATIM, swapping EnsureHandle() (which
    // returns the SESSION handle) for this facade's own _handle guard.
    public void Dispose()
    {
        IntPtr prev = Interlocked.Exchange(ref _handle, IntPtr.Zero);
        if (prev != IntPtr.Zero) DS3Native.ds3_s3_client_destroy(prev);
    }
}
```

### Anti-Patterns to Avoid
- **Reusing `EnsureHandle()` (the session handle) for S3 ops** — this IS the bug. The S3 methods on `DS3Session` (`ListBuckets` :164 … `CopyObject` :256) must be **removed** from `DS3Session` (D-02) and re-homed on `DS3DriveS3Client`.
- **Minting one S3 client per call** — D-01 mandates one cached client per drive. Per-call minting leaks handles and diverges from macOS caching.
- **Persisting the secret to SQLite** — `DS3SdkService` already routes the secret to Credential Manager only (`T-17-09-02`). The S3 client builder must re-hydrate from `CredentialStore.Load(accountId, "apiKey:{id}:secretKey")`, never read it from the `api_keys` table.
- **Catching `AccessViolationException` in the wizard** — it is a *corrupted-state exception*; .NET does not deliver it to `catch` blocks by default. The wizard's existing `try/catch` + `MapErrorCopy` (`DriveSetupViewModel.cs:108-117`) is correct **once the handle is right** — the fix is to stop the AVE from happening, not to catch it.

## Common Pitfalls

### Pitfall 1: `AccessViolationException` is uncatchable — the symptom hides the cause
**What goes wrong:** Passing `DS3Session*` where `DS3S3Client*` is expected makes Rust deref the wrong struct. The crash is an AVE, which .NET (since 4.0) treats as a *corrupted-state exception* and does **not** route to `try/catch`. The wizard's existing catch never fires; the process dies.
**Why it happens:** Both handles are opaque `IntPtr` in `DS3Native.cs` (intentional, see its header comment), so the type system can't catch the mix-up at compile time.
**How to avoid:** The fix is structural (mint the right handle), not defensive. After the fix, verify by deliberately passing bad credentials → expect a clean `DS3S3Exception` (InvalidAccessKeyId, code in 2001-2099), NOT an AVE.
**Warning signs:** Process exit with no managed stack trace; `0xC0000005` in Event Viewer.

### Pitfall 2: Endpoint field is currently dropped on the C# side
**What goes wrong:** `DS3AccountInfo` (`DS3AccountInfo.cs:19`) `[JsonIgnore]`s everything except `id`/`tenant_id`. The Rust `Account.endpoint_gateway` (`account.rs:81`, wire key `endpoint_gateway`) is in the JSON but never deserialized into the minimal record.
**Why it happens:** Phase 17 only needed the account *identity* for the credential-store scope key; it never needed the endpoint because S3 never worked.
**How to avoid:** Add `[property: JsonPropertyName("endpoint_gateway")] string EndpointGateway` to `DS3AccountInfo` (the full payload already carries it — the comment at `DS3AccountInfo.cs:11-13` notes the App layer "deserializes the complete object when it needs them"; now it needs the endpoint). Surface it via `AuthenticationService.CurrentAccount`.
**Warning signs:** S3 client built against an empty/`null` endpoint → all S3 calls fail with a transport error.

### Pitfall 3: Concurrent handle access (the `SemaphoreSlim(20,20)` ×2 reality)
**What goes wrong:** `FetchDataHandler` (download, `FetchDataHandler.cs:39`) and `UploadQueue` (upload, `UploadQueue.cs:33`) each own an **independent** `SemaphoreSlim(20,20)`. With both saturated, ~40 threads call into the single `DS3S3Client` handle concurrently. If the handle weren't thread-safe this would corrupt or race.
**Why it happens:** Phase-17 sync design bounds per-op concurrency, not aggregate, and both ops share one client.
**How to avoid:** This is **safe** — `DS3S3Client` wraps `aws_sdk_s3::Client`, which is `Clone + Send + Sync` (internally `Arc`-based) and is *already* driven concurrently by `futures::stream` in `ds3-s3/src/multipart.rs:9`. The C-ABI exports take `*const DS3S3Client` (shared `&`), and every method takes `&self`. **Document explicitly:** the handle may be shared by N threads; do not add a C#-side mutex around S3 calls (it would serialize and kill throughput). The only mutation point is *destroy*, which the `Interlocked.Exchange` guard makes single-shot.
**Warning signs:** None expected; if you see data races it means someone wrapped the handle in a non-thread-safe shim.

### Pitfall 4: Double-free / use-after-free on drive teardown
**What goes wrong:** If `DS3DriveS3Client.Dispose` runs while a sync op is mid-flight on another thread, the op derefs a freed handle.
**Why it happens:** `SyncHostedService.StopActiveAsync` (`SyncHostedService.cs:165`) cancels the CTS and stops the engine *before* tearing down — but the S3 client must be disposed **after** the engine fully stops, or an in-flight FETCH/upload races the free.
**How to avoid:** Dispose the `DS3DriveS3Client` **last** in `StopActiveAsync`, after `engine.StopAsync` + `provider.DisconnectAsync` complete (both already awaited). The `Interlocked.Exchange` guard makes double-dispose a no-op, but it does NOT protect a concurrent in-flight call — ordering does. Mirror macOS `shutdown()` which tears down clients after the cache is drained (`DS3Client.swift:220`).
**Warning signs:** Intermittent AVE only on drive removal / app shutdown.

### Pitfall 5: Rebuild-on-credential-change must actually rebuild the native client
**What goes wrong:** macOS `reloadDriveCredentials` (`DS3Client.swift:186`) rebuilds the `DS3S3Client` when `endpoint` or `apiKey`/`secretKey` change. If the Windows host caches the `DS3DriveS3Client` forever and only the *creds* change (e.g. API-key rotation, 403 self-heal), the stale handle keeps using revoked creds.
**Why it happens:** The handle is immutable (constructed from creds at build time); there is no "update creds in place" export.
**How to avoid:** When creds/endpoint change, `Dispose()` the old `DS3DriveS3Client` and `Create()` a fresh one (atomic swap under the host's `_lock`). Compare against the persisted creds exactly like macOS (`endpointChanged || keyChanged`, `DS3Client.swift:194-197`). For 17.1 the minimum is: build at host start from persisted creds, and rebuild if the persisted creds differ on a later start — full live-rotation hardening can lean on Phase 18.
**Warning signs:** `InvalidAccessKeyId` after an API-key reconcile that recreated the key.

### Pitfall 6: ARM64 marshalling parity
**What goes wrong:** The DLL is built for both `win-x64` and `win-arm64` (`build-dll-windows.ps1:51`). CI only tests x64 (`windows-build.yml:49`); ARM64 is manual-smoke only. A marshalling bug that only manifests on ARM64 (calling-convention or `nuint` width) would pass CI and fail on the real target.
**Why it happens:** `nuint`/`usize` is 64-bit on both win-x64 and win-arm64, and the ABI is `Cdecl` on both — so there is **no** expected ARM64-specific divergence here (unlike 32-bit). The risk is theoretical.
**How to avoid:** Keep the two new exports byte-identical in shape to the existing S3 exports (which already run on ARM64 for the *download* path that Phase 17 smoke-tested). Run the manual ARM64 smoke (D-07.2) as the parity gate. Do NOT introduce any `int`-width pointer or length param.
**Warning signs:** x64 CI green, ARM64 smoke AVE on the very first S3 call.

## Detailed Answers to Research Questions

### Q1 — FFI export shape, lifetime, marshalling, thread-safety
- **Signature:** `ds3_s3_client_new(endpoint, access_key, secret_key, region, out_handle: *mut *mut DS3S3Client, out_error: *mut i32) -> i32`. Each string is a `(*const u8, usize)` pair (UTF-8). Mirror `ds3_authenticate` (`c_exports.rs:127`).
- **`region` marshalling:** `region` is `Option<&str>` in `DS3S3Client::new`. Use the **existing** `ffi_opt_str` (`c_exports.rs:48`): null ptr OR zero len → `None` → Rust defaults to `"us-east-1"` (`client.rs:70`). C# passes `null, 0`. **No special-casing needed.**
- **Lifetime:** `Box::into_raw` on `new`, `Box::from_raw`+`drop` on `destroy` — identical to `ds3_session_destroy` (`c_exports.rs:201`). The C# `Interlocked.Exchange` guard makes destroy single-shot.
- **`Send + Sync` / concurrent safety:** YES. `DS3S3Client` wraps `aws_sdk_s3::Client` (`#[derive(Clone)] pub struct DS3S3Client { client }`, `client.rs:40`). `aws_sdk_s3::Client` is `Clone + Send + Sync` (internally `Arc`). The C-ABI takes `*const DS3S3Client` (shared `&`) and every S3 method takes `&self` + `block_on`. It is already driven concurrently via `futures::stream` in `multipart.rs`. **Safe to hold as a long-lived raw pointer and call from the `SemaphoreSlim(20,20)` engine (and the second SemaphoreSlim in the upload path) concurrently.** `new` returns `Self` (not `Result`) and does no I/O — so the only `?` in the export is the UTF-8 decode.

### Q2 — macOS parity model (what to mirror vs. diverge)
macOS `DS3Client.swift` two paths:
- **Lazy (main app):** `s3Client(forProject:iamUser:)` (`:130`) — cache keyed `"\(project.id)_\(user.id)"` (`:134`); on miss, `loadOrCreateDS3APIKeys` → `apiKey.apiKey`/`apiKey.secretKey`; endpoint from `account.endpointGateway` (`:171`); double-checked under `OSAllocatedUnfairLock` because the shared session handle's `connectS3` mutates creds (`:160-178`).
- **Eager (extension):** `init(drive:)` (`:74`) — loads persisted account + key, builds `driveS3Client` immediately (`:92`); `reloadDriveCredentials` (`:186`) rebuilds on `endpointChanged || keyChanged`.

**Windows mirror (D-01):** cache **per drive** (CONTEXT explicitly allows this divergence: "macOS caches per project+user; Windows per drive"). Credential derivation: `DS3SdkService.LoadOrCreateApiKeyAsync(user, projectName)` (`DS3SdkService.cs:83`) → `DS3ApiKey{AccessKey, SecretKey}`; secret re-hydrated from Credential Manager. Endpoint: `account.endpoint_gateway` (NEW field on `DS3AccountInfo`). **Legitimately diverge:** Windows has no shared-mutating session-handle problem (the C-ABI S3 client is fully independent of the session), so the Windows cache lock can be a plain `lock`/`SemaphoreSlim` guarding the dictionary — no double-check-under-lock-for-credential-clobbering subtlety. **Mirror exactly:** rebuild-on-change semantics (`reloadDriveCredentials` → Dispose+Create).

### Q3 — Credential timing & persistence (concrete seams)
- **Wizard time:** `DriveSetupViewModel.CreateDriveAsync` (`:208`) already calls `_sdk.LoadOrCreateApiKeyAsync(CurrentUser, SelectedProject.Name, ct)` — this reconciles/creates the key and persists secret→Credential Manager, metadata→`api_keys` table (`DS3SdkService.cs:134-163`). **This already happens; the phase just needs to USE the result to build the S3 client.**
- **Persistence location (clarification on D-05):** `ConfigStore` is **read-only build-time config** (`ConfigStore.cs:17` — coordinator URL, log level, key-name prefix) and **cannot** store per-drive creds. The actual writable per-drive credential store is **`CredentialStore`** (Windows Credential Manager) for the secret + the SQLite `api_keys` table for non-secret metadata + the `drives` persistence (`DriveManagementService`) for the anchor. **Recommendation:** persist nothing new — the creds are already persisted by the existing reconciliation; the S3 client builder re-derives them (re-hydrate secret from `CredentialStore.Load(accountId, "apiKey:{id}:secretKey")`, `DS3SdkService.cs:184`). DPAPI (Phase 18) only changes the *encryption-at-rest*, not the seam.
- **Sync host build-at-startup:** `SyncHostedService.StartDriveAsync` (`:129`) is where the per-drive `DS3DriveS3Client` is built (from persisted creds + endpoint) before `engine.StartAsync`, and where the rebuild-on-change check lives. Inject a per-drive S3-client factory into the host (or build inline) and dispose it in `StopActiveAsync` (`:165`, last, per Pitfall 4).

### Q4 — cfapi routing seam (minimal clean change)
The 6 sync ops already route through **`IDS3SessionAccess`** (`IDS3SessionAccess.cs:15`): `ListObjects`, `DownloadObject`, `UploadObject`, `DeleteObject`, `CopyObject` (+ `AccountId`). Consumers: `SyncEngine` (`:26,116,215,221`), `UploadQueue` (`:34`), `FetchDataHandler` (`:36`). Today `AuthenticationService` implements `IDS3SessionAccess` by routing to `EnsureSession()` (the session handle — the bug, `AuthenticationService.cs:216-237`).

**Recommended minimal change:** Do **not** widen `IDS3SessionAccess` (its signatures have no drive context, so a drive-keyed cache inside `AuthenticationService` would be awkward). Instead, since `SyncHostedService` already constructs everything **per drive** (`:142-150`) and now also owns the per-drive `DS3DriveS3Client`, **introduce a thin per-drive adapter** (`DriveS3SessionAccess : IDS3SessionAccess`) that wraps one `DS3DriveS3Client` and is passed into the per-drive `SyncEngine`/`UploadQueue`/`CfApiProvider` in place of the shared `_session`. This keeps the seam unchanged, gives each drive its own correctly-scoped client, and matches macOS (per-drive `driveS3Client`). The DI registration at `App.xaml.cs:141` then changes from "the shared `AuthenticationService` singleton" to "the host builds a per-drive adapter."

**Threading/ownership:** the per-drive adapter holds the `DS3DriveS3Client`; the host owns the adapter's lifetime; dispose-last on teardown (Pitfall 4). The handle is shared across the engine's threads (Pitfall 3 — safe).

### Q5 — Wizard error UX (D-06)
**Current crash path:** `DriveSetupViewModel.SelectProject` (`:127`) → `LoadBucketsAsync` (`:99`) → `_sdk.GetBucketsAsync` (`DS3SdkService.cs:54`) → `_session.ListBuckets()` → `DS3Session.ListBuckets` (`:164`) passes the session handle into `ds3_list_buckets` → AVE. The view-model **already** has the correct shell: `try/catch` that sets `CreationError = MapErrorCopy(ex)` and stays on the step (`:108-117`), and `MapErrorCopy` (`:250`) already distinguishes `DS3S3Exception` ("can't access this bucket") from `DS3TransportException` ("check your connection").
**The fix is upstream:** once `GetBucketsAsync` routes through a valid `DS3DriveS3Client`, a bad key returns a clean `DS3S3Exception` (code 2001-2099 via `DS3ExceptionFactory`, `:48`) instead of an AVE — and the existing catch + inline `CreationError` binding + Retry already work. **Add:** (a) ensure `InvalidAccessKeyId` maps into the 2001-2099 S3 range in the Rust error mapping so it surfaces as `DS3S3Exception` (verify against `ds3-models` error codes); (b) a dedicated copy line distinguishing "wrong credentials" from "no access" if product wants it (discretionary); (c) wire the Bucket step's Retry button to re-invoke `LoadBucketsCommand`. No new exception types — reuse `DS3S3Exception`/`DS3TransportException`/`DS3ExceptionFactory`.

### Q7 — Pitfalls/landmines
Covered in Common Pitfalls 1-6. The two that most threaten the criterion #5 silent round-trip:

## Security Domain

> `security_enforcement` absent in config ⇒ enabled. This phase moves S3 **credentials** across the FFI boundary, so input-validation and crypto/secret-handling categories apply.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | Unchanged — login/2FA already verified (Phase 17). |
| V3 Session Management | no | Session handle untouched (D-02 keeps it auth-only). |
| V4 Access Control | yes | S3 access is scoped by the per-project API key; the bucket-access-denied path surfaces as `DS3S3Exception` (no privilege escalation). |
| V5 Input Validation | yes | All FFI strings validated as UTF-8 via `ffi_str`/`ffi_opt_str` (returns `DS3Error::Encoding`, code 1004, on bad bytes). Lengths always computed by `M.Len` from byte count, never caller-supplied (`DS3Session.cs:396`). |
| V6 Cryptography / Secret Storage | yes | The API-key **secret** never lands in SQLite (`T-17-09-02`); it lives only in Credential Manager (`CredentialStore`). The S3 client re-hydrates it transiently and the secret crosses the FFI as a UTF-8 buffer that the C# side does not retain. DPAPI-at-rest is Phase 18 (deferred). |

### Known Threat Patterns for Rust C-ABI ↔ C# P/Invoke

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Wrong-type handle deref (the current bug) | Tampering / DoS | Mint the correct `DS3S3Client` handle; never pass `DS3Session*` to S3 exports (D-02). |
| Panic unwinding across FFI (UB) | DoS | `ffi_guard!` wraps both new exports → returns -2, no unwind. |
| Double-free / use-after-free on the S3 handle | Tampering / DoS | `Interlocked.Exchange` single-shot dispose (Pitfall 4) + dispose-last ordering in `SyncHostedService.StopActiveAsync`. |
| Secret leakage via logs / error messages | Information Disclosure | `DS3ExceptionFactory.UnknownCode` logs the numeric code only, never the raw message (`T-17-05-03`); the wizard `MapErrorCopy` shows fixed copy, never server text (`T-17-09-05`). `DS3S3Client::new` is `#[tracing::instrument(skip(access_key, secret_key))]` — secrets already excluded from traces (`client.rs:54`). |
| Concurrent corruption of the shared handle | Tampering | `aws_sdk_s3::Client` is `Send + Sync`; shared `&self`, no C#-side mutex (Pitfall 3). |
