### 17.1-UAT-01 — Bucket listing fails with server error (1002), masked as empty state [OPEN]
severity: high (blocks drive creation) · scope: OUT of phase-17.1 S3-FFI (keyvault/IAM path)
symptom: Selecting "Moschet Personal" (which genuinely has buckets) logged
`Failed to load buckets: [1002] There was an error with the server` after 5×
`DS3AuthenticationException`. UI showed the benign "No buckets in this project" empty state.
diagnosis: The failure is in the IAM-token/keyvault reconcile
(`DS3SdkService.GetBrowseClientAsync` → `LoadOrCreateApiKeyAsync` → `ForgeIamToken` /
`LoadApiKeys`), which runs BEFORE the new `DS3DriveS3Client` is built — so the phase's S3-FFI
work is not implicated. Rust `ds3-http/keys.rs` returns `DS3Error::ServerError { status, body }`
on any non-2xx keyvault response; the FFI boundary collapses it to the generic code-1002 message,
**discarding the HTTP status + body** that would pinpoint the cause. Needs a live trace capture or
a focused debug session — not a blind fix. Likely a Phase 16/17 keyvault-path or backend issue,
first exercised end-to-end on real hardware here.
status: open — DIAGNOSTIC WIRED (2026-06-02). The FFI now carries the full server detail
across the boundary so the next run reveals the real cause:
  - Rust `DS3Error::detail()` includes HTTP status + response body for `ServerError`
    (terse `Display` left intact so `ds3_error_code` is unaffected).
  - `ffi_guard!` stashes `e.detail()` in a thread-local; new export `ds3_last_error_message`
    reads+clears it; `DS3Session.Check` attaches it to the thrown exception.
  - Net effect: the existing `LogError("Failed to load buckets: {Message}")` will now print
    `[1002] Server error: HTTP <status>: <body>` in the VS Output window.
  - ARM64 `ds3_ffi.dll` rebuilt + export verified; UI still shows fixed copy (no leak).
Next: Stop → F5, reproduce the bucket step, paste the new `[1002] Server error: HTTP …` line.

ROOT CAUSE FOUND + FIXED (2026-06-02). The diagnostic revealed
`[1002] Server error: HTTP 401: {"message":"unauthorized","params":null}` on the
IAM-token forge. macOS comparison (current Swift `handle.forgeIamToken(userId: user.id)`,
pre-Rust-port Swift `?user_id=\(user.id)`, and Rust `?user_id={user_id}`) shows macOS ALWAYS
forges for a project IAM user id — `selectedIAMUser(forProject:) == project.users.first`
(TreeNavigationView.swift) — NEVER the account id. Windows diverged in two places:
  1. `DS3Project` dropped the `users` array (only mapped 3 of the 4 fields the Rust
     `Project` emits), so the project's IAM users never reached C#.
  2. With no users, `DS3SdkService.GetBrowseClientAsync` (and `CreateDriveAsync`) fabricated
     `new DS3IAMUser(AccountId, AccountId, …)` and forged for the account id → coordinator
     returns 401 (the `_refresh` cookie can only forge tokens for the account's IAM users).
Fix (pure C#, mirrors macOS):
  - `DS3Project` now carries `Users` (deserializes `users`).
  - `GetBrowseClientAsync` forges for `project.Users[0]` (the browse 401 — this test).
  - `CreateDriveAsync` forges for `SelectedProject.Users[0]` AND persists that id in the
    `DS3SyncAnchor`, so the running drive's `DriveS3CredentialProvider` (which reconstructs
    from `anchor.IamUserId`) forges correctly too — not just the wizard.
Validated: Tests project compiles; 14/14 DriveSetupViewModel tests pass (incl. CreateDrive).
No Rust/DLL change needed.

UPDATE — 401 → 403 (2026-06-02). Re-test confirmed the UI fixes (error InfoBar + Retry now
show; Continue disabled) and the 401 is gone — but the forge target now returns
`HTTP 403 {"statusCode":403,"message":"Forbidden resource"}`. The account can't act for
`project.Users[0]` for "Moschet Personal". macOS handles this with an IAM-USER PICKER
(TreeNavigationView/BucketListView list project.users with a "(root)" tag; default
project.users.first, user can switch). Windows had no picker. Added (all C#/XAML, no Rust):
  - `DS3IAMUser` now carries `IsRoot` (+ `DisplayLabel` "username (root)").
  - Bucket step has an "IAM user" ComboBox (AvailableUsers); default = the project ROOT user
    (better default than blind [0]); switching re-lists buckets (SelectedIamUser →
    OnSelectedIamUserChanged). The chosen user flows to browse AND the persisted anchor.
  - `GetBucketsAsync(project, user)` + per-(project,user) browse-client cache.
  - Debug logs: project's full user list (id/name/root), which user is forged, and
    forge-OK-vs-keyvault bracketing so the next 403 pinpoints the failing call.
Validated: 14/14 wizard tests pass.

ROOT CAUSE OF THE 403 — FOUND + FIXED (2026-06-02). The new logs were decisive:
  - "Wizard: selected project 'Moschet Personal' with 1 IAM user(s): [ROOT(root=True)]" — ROOT is
    the ONLY user (confirmed by the user), so the picker default is already correct; the 403 was
    NOT a wrong-user problem.
  - "Reconcile: forge OK; listing keyvault API keys …" was the last line before the 403 → the
    forge SUCCEEDS; the failure is the keyvault LoadApiKeys call.
The bug: the C-ABI `ds3_forge_iam_token` returns the forged token as JSON
(`{"token","exp","exp_date"}`), and macOS (UniFFI) parses it and sends the `.token` JWT as the
Bearer. Windows' `DS3Session.ForgeIamToken` returned the RAW JSON string and passed it straight to
keyvault as `Authorization: Bearer {"token":…}` → the coordinator rejects the malformed bearer
with HTTP 403. Fix: `ForgeIamToken` now parses the JSON and returns the bare JWT (`doc.RootElement
.GetProperty("token")`). Pure C#, no Rust/DLL change. Re-test: Stop → F5 → select a project →
buckets should finally list (forge + keyvault both authenticate with the real JWT).

CONFIRMED: buckets list (keyvault returned 113 keys; wizard shows real buckets, Continue enabled).

### Prefix-browse crash on bucket select — FIXED (2026-06-02)
Selecting a bucket advanced to the Prefix step and threw
`JsonException: could not be converted to List<DS3Object>` in
`DS3DriveS3Client.ListObjects` / `ListChildPrefixesAsync`. Same class as the token bug — a JSON
shape mismatch. The native `ds3_list_objects` returns an `S3ListingResult` object
(`{ objects, common_prefixes, next_continuation_token, is_truncated }`), but C# deserialized a
bare `List<DS3Object>`. Also, with a delimiter the child folders come back in `common_prefixes`,
not as trailing-slash objects. Fix (pure C#):
  - New `DS3ObjectListing` record matching the result shape.
  - `ListObjects` parses the listing and returns `.Objects` (keeps the sync engine / cfapi
    provider / integration-test callers working); added `ListObjectsListing` for the full result.
  - The prefix tree now uses `listing.CommonPrefixes` (the real S3 folder source).
  - `DS3Object.LastModified` made nullable (objects can lack a date - was a latent crash).
Validated: Core+Sync+ViewModels+Tests compile; 14/14 wizard tests pass. Re-test: select a bucket
then the Prefix step should list child folders without crashing.

### 17.1-UAT-06 — Drive folder is empty in Explorer (no placeholders) [FIXED]
symptom: After drive creation the "Cubbit DS3 Drive" sync root appeared in Explorer but was empty —
no files or folders, even though the bucket/prefix has content.
root cause: TWO gaps. (1) The provider only listed `.Objects` and never the delimiter
`common_prefixes`, so folders were invisible. (2) `CfCreatePlaceholders` was never called — the
provider wrote placeholder DB rows but never materialized any on-disk reparse points, which is what
Explorer actually renders.
fix (macOS-parity + cfapi best practice): switched to **on-demand population**, matching the macOS
`S3Enumerator` (lazy, direct-children-only) rather than an eager tree walk:
  - Sync root now registers with `PopulationPolicy = Full` (on-demand) instead of `AlwaysFull`.
  - New `FetchPlaceholdersHandler` wired as a 5th callback (`CF_CALLBACK_TYPE_FETCH_PLACEHOLDERS`).
    When Explorer first opens a directory the platform fires it; we list that ONE S3 level (objects
    + common prefixes, paginated, `.ds3keep` markers skipped) and hand the platform a placeholder per
    child via `CfExecute(TRANSFER_PLACEHOLDERS)` (`SafeNativeArray<CF_PLACEHOLDER_CREATE_INFO>`).
    Files are cloud-only placeholders that hydrate on first open through the existing FETCH_DATA path.
  - `IDS3SessionAccess.ListObjectsListing` added so folders reach the sync layer.
  - Sub-prefix correctness: on-disk paths are relative to the drive's S3 prefix, so all cfapi handlers
    (fetch-data / fetch-placeholders / file-close / rename / delete) now re-apply the drive prefix via
    `PathValidation.S3KeyFromNormalizedPath` to form the full S3 key — previously a drive scoped to a
    sub-prefix would have hit the wrong key.
  - `SyncEngine.PollOnceAsync` now includes common prefixes in the remote set so the folders just
    populated are not pruned as phantom remote deletions on the next poll.
validated: Core+Sync+ViewModels+Tests compile clean (0 warnings under TreatWarningsAsErrors); 146/146
unit tests pass. Re-test (Stop → F5): open the drive in Explorer — top-level files + folders should
appear; opening a subfolder lists its children; double-clicking a file hydrates it.
note (follow-up, not blocking): incremental on-disk reflection of NEW remote files (creating
placeholders during a poll for keys added after first browse) is not yet wired — first-browse
population + hydration is. The poll keeps the DB fresh and no longer prunes folders.

### 17.1-UAT-02 — Bucket-load error never displayed (InfoBar bug) [FIXED]
symptom: On a load failure the error InfoBar stayed hidden; only the empty state showed.
root cause: `BucketSelectionPage.xaml` bound the InfoBar `Visibility` to the `CreationError`
*string* via `BoolToVisibilityConverter`, whose `value is bool` test is always false for a string
→ always `Collapsed`.
fix: InfoBar now drives `IsOpen` off `CreationError` via `NotNullToBoolConverter` (the same
pattern LoginPage uses); broken `Visibility` binding removed.

### 17.1-UAT-03 — Empty "No buckets" state masks load failures [FIXED]
root cause: `HasNoBuckets(count, isLoading)` ignored `CreationError`, so a failed load rendered the
"create a bucket" empty state instead of the error.
fix: predicate is now `HasNoBuckets(count, isLoading, error)` — empty state shows only when there
is genuinely no error.

### 17.1-UAT-04 — Continue enabled with no buckets [FIXED]
root cause: wizard `PrimaryButton` was hardcoded `IsEnabled="True"`.
fix: `DriveSetupWizardPage.UpdateButtons()` now disables Continue on the Bucket step unless
`Buckets.Count > 0 && !IsLoadingBuckets`; re-evaluated when Buckets/IsLoadingBuckets/CreationError
change (not only on step transitions).

### 17.1-UAT-05 — Enter does not submit Login / MFA forms [FIXED]
fix: `LoginPage` Email/Password fields and `TwoFactorPage` code field now handle `Enter`
(`KeyDown` → `LoginCommand` / `VerifyCommand` when `CanExecute`), matching macOS `onSubmit`.
