## Fixed Issues

### CR-01: Plaintext S3 secret retained for the full drive lifetime

**Files modified:** `windows/DS3Drive.Sync/Hosting/SyncHostedService.cs`
**Commit:** db713c6
**Applied fix:** Replaced the long-lived `DriveS3Credentials Creds` field on the `ActiveDrive`
record with a non-reversible `string CredsFingerprint` (SHA-256 over `endpoint|access|secret`).
The fingerprint is computed once, at the single point the live secret is already in hand
(immediately around `DS3DriveS3Client.Create`), and the `DriveS3Credentials` instance is never
retained afterward. The rebuild-on-change check now compares fingerprints
(`existing.CredsFingerprint == CredsFingerprintOf(creds)`) instead of comparing the plaintext
secret by value-equality on every `StartDriveAsync`. `DS3DriveS3Client.Create` remains the sole
consumer of the plaintext `SecretKey`. **Requires human verification:** the change alters
credential change-detection semantics (security-sensitive); confirm the fingerprint correctly
triggers a rebuild on endpoint/key rotation and never falsely short-circuits.

### WR-01: Use-after-free window in the wizard-browse dispose path

**Files modified:** `windows/DS3Drive.ViewModels/Services/DS3SdkService.cs`
**Commit:** 813df70
**Applied fix:** Added an in-flight browse-operation gate mirroring the sync host's dispose-last
discipline. `EnterBrowseOperation`/`ExitBrowseOperation` (both under `_browseLock`) track a
running-operation count and a `ManualResetEventSlim _drained`; `GetBucketsAsync` and
`ListChildPrefixesAsync` now wrap their `Task.Run(() => client.List...)` calls in
enter/finally-exit. `Dispose()` now runs in three phases: (1) set `_disposed` under the lock so
no NEW operation can start touching a handle about to be freed (`EnterBrowseOperation` throws
`ObjectDisposedException`), (2) `_drained.Wait()` outside the lock to drain outstanding worker
calls, (3) free the native handles. Also fixed the unlocked read of `_currentBrowseClient` in
`ListChildPrefixesAsync` by snapshotting it under `_browseLock` (it is mutated under that lock
in `GetBrowseClientAsync`). **Requires human verification:** non-trivial concurrency change;
confirm no deadlock between `_browseLock` and `_drained` and that the drain correctly blocks a
shutdown that races an in-flight browse.

### WR-02: Native S3-client (and CTS) handle leaks when drive teardown throws

**Files modified:** `windows/DS3Drive.Sync/Hosting/SyncHostedService.cs`
**Commit:** db713c6
**Applied fix:** Moved `active.Cts.Dispose()` and `active.S3.Dispose()` out of the `try` body and
into a `finally` block in `StopActiveAsync`, so the native `DS3S3Client` handle and the CTS are
disposed unconditionally even when an earlier `await` (`Engine.StopAsync`,

ordering for the S3 handle is preserved (it is the last statement in the `finally`).

### WR-03: `CopyObject` silently discards its destination-bucket argument

**Files modified:** `windows/DS3Drive.Core/DS3DriveS3Client.cs`
**Commit:** 727cc00
**Applied fix:** Added an explicit guard at the top of `CopyObject`: when
`!string.Equals(srcBucket, dstBucket, StringComparison.Ordinal)` it throws
`NotSupportedException("Cross-bucket copy is not supported by the current ds3_copy_object ABI.")`
instead of silently writing to the source bucket. This replaces the prior `_ = dstBucket;`
discard with a real consumer of the argument, so a cross-bucket request now fails loudly rather
than misplacing data. Current callers all pass the same bucket twice, so behavior is unchanged
for them.

## Skipped Issues

### WR-04: `CancellationHandle` parameter accepted then silently dropped on download/upload

**File:** `windows/DS3Drive.Core/DS3DriveS3Client.cs:121-137`, `140-157`
**Reason:** skipped — not safely auto-fixable; requires a design decision. The reviewer's two
options are (a) thread a `*const CancellationHandle` through the FFI, which is a Rust + C-ABI
change to `ds3_download_object`/`ds3_upload_object` (the DLL is MSVC/clang-gated on this dev box
and cannot be compiled/verified here), or (b) remove the `cancel` parameter from the C#
signatures. Option (b) is a public-API change that ripples across `DS3DriveS3Client`,
`IDS3SessionAccess`, `DriveS3SessionAccess`, the call sites in `FetchDataHandler` /
`UploadQueue`, and the integration tests (all currently pass `cancel: null`), and it forecloses
the intended cancellation roadmap rather than merely surfacing the gap. Neither path is a low-
risk mechanical edit, so this is left for a human to decide and implement (cancellation-through-
FFI vs. signature narrowing) rather than applying a risky change.
**Original issue:** `DownloadObject`/`UploadObject` accept `CancellationHandle? cancel` and
discard it (`_ = cancel;`); the underlying exports take no cancellation parameter, so a caller
that mints a handle and passes it in cannot actually cancel an in-progress transfer — a silent
no-op contract gap that the dropped parameter hides from callers.
