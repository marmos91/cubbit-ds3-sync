# Phase 17.1: Windows S3-Client FFI Wiring + Sync Enablement - Context

**Gathered:** 2026-06-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Wire the S3 client across the FFI (C ABI) boundary so the Windows app can list buckets, browse prefixes, and run the cfapi sync engine end-to-end — completing the sync promise of Phase 17, which delivered the shell, auth, projects, and cfapi plumbing but left S3 operations unreachable.

**Root cause being fixed:** every S3 export (`ds3_list_buckets`, `ds3_list_objects`, `ds3_head_object`, download/upload/delete/copy) expects a `*const DS3S3Client` handle, but no FFI export mints one. The C# facade currently passes the `DS3Session` handle instead, so Rust dereferences the wrong struct → `AccessViolationException` at the wizard's Bucket step, blocking all sync. `DS3S3Client::new(endpoint, access_key, secret_key, region)` already exists in `ds3-s3` but is unexposed.

**Guiding principle (user directive 2026-06-01): follow the same UX/behavior as macOS.** The macOS `DS3Client` S3 flow (`apple/DS3Lib/Sources/DS3Lib/DS3Client.swift`) is the canonical reference for credential derivation, client caching, rebuild-on-credential-change, and error routing. Windows should mirror it, not invent a new model.

**In scope:** the 5 locked success criteria in ROADMAP.md §"Phase 17.1" — mint/destroy FFI exports for `DS3S3Client`, derive creds from the API-key flow per drive, route wizard bucket/prefix browsing and all six cfapi sync ops (list/head/download/upload/delete/copy) through the S3 handle, and complete a bidirectional first-run round-trip on native ARM64.
**Out of scope (Phase 18):** DPAPI credential storage (POL-03), multi-drive beyond what falls out naturally (POL-04), conflict resolution (POL-08), cross-FFI logging (POL-01), error-surface hardening beyond the wizard step.
</domain>

<decisions>
## Implementation Decisions

### S3 Client Ownership & Lifecycle
- **D-01:** Introduce a new per-drive `DS3DriveS3Client` C# facade that owns exactly one native `DS3S3Client` handle (minted via the new `ds3_s3_client_new` export). One instance per drive, cached and reused for that drive's lifetime; disposed together with the drive's sync host. This mirrors macOS `driveS3Client` / `s3Client(forProject:iamUser:)` caching (macOS caches per `project+user`).
- **D-02:** `DS3Session` stays **auth/session-only** — it no longer routes S3 ops. Remove/replace the Wave-1 stopgap where `DS3Session.ListBuckets/ListObjects/...` pass `EnsureHandle()` (the session handle) into S3 exports.
- **D-03:** The C# facade owns and disposes the `DS3S3Client` handle (criterion #1): `ds3_s3_client_new` on construction, `ds3_s3_client_destroy` on `Dispose`, with the same handle-guard discipline as `DS3Session` (short-circuit if the handle is gone).

### Credential Derivation & Timing
- **D-04:** Credentials come from the **API-key flow per project/drive** (criterion #2), NOT the raw IAM session token. Source = the wizard's existing API-key reconciliation + `account.endpointGateway` (matching macOS `loadOrCreateDS3APIKeys` → `apiKey.apiKey` / `apiKey.secretKey` / `endpointGateway`).
- **D-05:** Timing: reconcile/create the API key at **wizard time**, persist the per-drive creds (ConfigStore for now — DPAPI deferred to Phase 18), and have the **sync host build the S3 client at startup** from persisted creds. Rebuild the client when credentials/endpoint change, mirroring macOS `reloadDriveCredentials`.

### Wizard S3 Error UX
- **D-06:** When bucket listing fails (bad key / network) at the Bucket step that previously hard-crashed: **stay on the step, show an inline friendly error mapped from the typed `DS3S3Exception`** (distinguish e.g. `InvalidAccessKeyId` from transport/network), with a **Retry** button. No crash, no loss of wizard progress. Reuse the existing exception hierarchy (`DS3S3Exception`, `DS3ExceptionFactory`).

### Verification
- **D-07:** Two-layer verification of criterion #5:
  1. **Automated C# integration test** (`Category=Integration`, gated on Cubbit secrets exactly like the existing "C# P/Invoke Tests (Windows)" CI job) exercising list/head/upload/download/delete/copy **through the new `DS3DriveS3Client` handle** against real Cubbit S3.
  2. **Manual ARM64 smoke checklist** item (in the style of Phase 17's `manual-smoke-D-33.md`) covering the full first-run path: login → 2FA → wizard → create drive → bidirectional sync round-trip.

### Claude's Discretion
- Region/endpoint argument value for `ds3_s3_client_new` (Cubbit is S3-compatible; pick the default the macOS path uses — region is `Option` in `DS3S3Client::new`).
- Exact C# marshalling shape of the new exports (follow the established `DS3Native` string/`out`-param + `ffi_guard` panic-guard patterns).
- Concurrency limits for routed sync ops (reuse the Phase-17 `SemaphoreSlim(20,20)` discipline unless research says otherwise).
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `DS3S3Client::new(endpoint, access_key, secret_key, region)` (`core/ds3-s3/src/client.rs:55`) — fully implemented; this phase only needs to expose it + a destructor across the C ABI (no new S3 logic in Rust).
- `DS3Session` handle-owning + `EnsureHandle()` guard pattern — copy this shape for `DS3DriveS3Client`'s lifecycle/disposal.
- Exception hierarchy (`DS3S3Exception`, `DS3ExceptionFactory`, `DS3TransportException`) — already maps Rust error codes to typed C# exceptions; reuse for the inline wizard error.
- Phase-17 wizard API-key reconciliation + cfapi `SyncEngine`/`SyncHostedService` — the host that will own and build the per-drive S3 client.

### Established Patterns
- FFI: `#[no_mangle] extern "C"` + `ffi_guard!(out_error, …)` + `write_ffi_string` (out-param JSON) in `c_exports.rs`; C# side: `DS3Native` P/Invoke with `out IntPtr json, out nuint len, out int err`. New exports must follow both.
- Native DLL is built per-Platform and staged into `DS3Drive.Core/runtimes/win-<arch>/native/` (CI builds via `core/scripts/build-dll-windows.ps1`).

### Integration Points
- New `ds3_s3_client_new`/`_destroy` in `core/ds3-ffi/src/c_exports.rs` → bindings in `DS3Drive.Core/Generated/DS3Native.cs` → owned by `DS3DriveS3Client` (new) → consumed by the wizard's Bucket/prefix browse and by the cfapi sync engine via `IDS3SessionAccess` (or a new S3 access seam).
</code_context>

<specifics>
## Specific Ideas

- **Mirror macOS UX explicitly** (user directive): the per-drive cached client, lazy/persisted creds, rebuild-on-change, and the project→bucket→prefix browsing experience should match `DS3Client.swift` so Windows feels identical to macOS at the S3 boundary.
- The bidirectional round-trip is the acceptance bar: a created drive must hydrate cloud-only files and upload local changes against real Cubbit S3 on native ARM64.
</specifics>
