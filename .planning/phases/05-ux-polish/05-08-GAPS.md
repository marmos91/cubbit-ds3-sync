## Gap 1: Drive setup wizard has no recovery when session token expires

**Severity:** Medium (user-visible, produces a dead-end state)

**Symptom:**
During the "Add Drive" wizard flow, if the session token expires while the user is browsing the tree (project → bucket → prefix), the right detail pane shows a red `"The session token expired"` label with no recovery action. The Continue button is disabled (no selection possible) and there is no "Sign in again", retry, or back-to-login path. The only recovery is to close the wizard window, open Preferences → Account → Sign out, sign in again, and restart the flow.

**Root cause:**
`DS3Drive/Views/Sync/Views/TreeNavigationView.swift:539` renders `viewModel.error.localizedDescription` as a static text label. When `DS3Client.listBuckets()` / `listObjects()` throws `DS3AuthenticationError.tokenExpired`, the error bubbles from `expandProject`, `expandBucket`, `expandFolder`, and dead-ends on screen with no affordance.

The ingredients for a fix already exist:
- `DS3Lib/Sources/DS3Lib/DS3Authentication.swift:218` — `refreshIfNeeded(force:)` can refresh via the stored refresh cookie
- A proactive timer already calls it periodically (line 202-208), but not before wizard actions

## Proposed Fix — Two Layers

### Layer 1: Auto-refresh before S3 calls (transparent recovery)

In `TreeNavigationView.swift`, wrap the `getOrCreateS3Client()` path (used in `expandProject`, `expandBucket`, `expandFolder`) with `try? await authentication.refreshIfNeeded()` before the S3 call. If the refresh token is still valid, the user never sees an error — the wizard just works.

Apply the same pattern in:
- `DS3Drive/Views/Sync/ViewModels/SyncAnchorSelectionViewModel.swift:79` (`loadBuckets`)
- `DS3Drive/Views/Sync/ViewModels/SyncAnchorSelectionViewModel.swift:107` (`listFoldersForCurrentBucket`)
- `DS3Drive/Views/Sync/ViewModels/ProjectSelectionViewModel.swift` (project loading)

### Layer 2: Recovery action on authentication failure

When `refreshIfNeeded()` also fails (refresh token expired or revoked), render a "Sign in again" button below the error text in TreeNavigationView. The button should:
1. Call `authentication.logout()`
2. Dismiss the wizard window
3. Route the user back to the login flow

Pattern:
```swift
if let error = viewModel.error {
    VStack(spacing: DS3Spacing.sm) {
        Text(error.localizedDescription)
            .font(DS3Typography.caption)
            .foregroundStyle(DS3Colors.statusError)

        if error is DS3AuthenticationError {
            Button("Sign in again") {
                Task {
                    await authentication.logout()
                    dismiss()
                }
            }
            .buttonStyle(SecondaryButtonStyle())
        }
    }
    .padding(.horizontal, DS3Spacing.lg)
    .padding(.bottom, DS3Spacing.sm)
}
```

- `DS3Drive/Views/Sync/ViewModels/SyncAnchorSelectionViewModel.swift` — add refreshIfNeeded in loadBuckets/listFoldersForCurrentBucket
- `DS3Drive/Views/Sync/ViewModels/ProjectSelectionViewModel.swift` — add refreshIfNeeded in project loading
- `DS3Drive/Assets/Localizable.xcstrings` — add "Sign in again" / "Accedi di nuovo"

   - ✗ "Couldn't check for updates: {error message}" with a Retry button

3. **Optional:** Show the `lastCheckDate` as subtitle in Preferences → Updates section ("Last checked: 2 minutes ago") so users can confirm it actually ran.

**Files to Modify:**

- `DS3Drive/Views/Tray/ViewModels/DS3DriveViewModel.swift` — expose update checker state and a `checkForUpdates()` action that surfaces result

## Gap 32: `weak let weakSelf` captures flagged for data races under Swift 6

**Severity:** Medium (Swift 6 concurrency warning that becomes a build error when the project's `SWIFT_STRICT_CONCURRENCY=complete`; only surfaced after Plan 05-09 era changes to the weakSelf captures)

**Symptom:**
```
DS3Drive/Views/Tray/ViewModels/DS3DriveViewModel.swift:133:34 Sending 'weakSelf' risks causing data races
DS3Drive/Views/Tray/ViewModels/DS3DriveViewModel.swift:278:38 Sending 'weakSelf' risks causing data races
```

Both captures live inside `Timer.scheduledTimer` callbacks that use `MainActor.assumeIsolated { guard let self = weakSelf else { return } ... }`. Xcode's Swift 6 checker flags this as a sending violation because the `@Sendable` timer closure captures a weak reference to a `@MainActor`-isolated type, and there's no proof to the compiler that the weak reference can be safely crossed between isolation domains.

**History:**
1. The captures were originally `nonisolated(unsafe) weak var weakSelf = self` — compiled cleanly
2. SwiftLint flagged "Weak variable 'weakSelf' was never mutated" → changed to `weak let`
3. Later Xcode warned `'nonisolated(unsafe)' is unnecessary for a constant with 'Sendable' type 'DS3DriveViewModel?'` → dropped `nonisolated(unsafe)`
4. Swift 6 checker now flags the remaining `weak let weakSelf = self` as a data race risk

So the variable keeps getting tweaked to silence one warning and enable another. The underlying design — a `@MainActor` class scheduling a Timer that captures a weak self — is the real culprit.

**Proposed Fix (pick ONE, document the choice):**

### Option A — Restore `nonisolated(unsafe)` and suppress both warnings via documentation

```swift
// nonisolated(unsafe) is necessary because the Timer closure is @Sendable
// and captures a weak reference to a @MainActor class. The MainActor.assumeIsolated
// block below guarantees the self-access runs on the main runloop where the timer
// fires. SwiftLint's "never mutated" and Swift 6's "sending" warnings are both
// false positives for this specific pattern.
// swiftlint:disable:next identifier_name
nonisolated(unsafe) weak let weakSelf = self
```

Add `// swiftlint:disable:next` directives to silence the "never mutated" lint.

### Option B — Replace `Timer.scheduledTimer` with Swift Concurrency (recommended)

Use a `Task` with `Task.sleep(for:)` instead of Timer. The task inherits the enclosing `@MainActor` isolation so no cross-domain send is needed:

```swift
// Replace this:
nonisolated(unsafe) weak let weakSelf = self
self.transferStatsResetTimer = Timer.scheduledTimer(
    withTimeInterval: DefaultSettings.Tray.driveStatsReset,
    repeats: false
) { _ in
    MainActor.assumeIsolated {
        guard let self = weakSelf else { return }
        self.lastReportedSize.removeAll()
        // ...
    }
}

// With this:
self.transferStatsResetTask?.cancel()
self.transferStatsResetTask = Task { [weak self] in
    try? await Task.sleep(for: .seconds(DefaultSettings.Tray.driveStatsReset))
    guard !Task.isCancelled, let self else { return }
    self.lastReportedSize.removeAll()
    // ...
}
```

Same treatment for the `idleDebounceTimer` at line 278. Requires renaming timer properties to task properties and updating `invalidate()` sites to `.cancel()`.

### Option C — Keep Timer, manually dispatch to MainActor

```swift
Timer.scheduledTimer(withTimeInterval: ..., repeats: false) { _ in
    Task { @MainActor [weak self] in
        guard let self else { return }
        self.lastReportedSize.removeAll()
    }
}
```

This loses the "fire synchronously on main runloop" guarantee but avoids the weakSelf pattern entirely.

**Recommendation:** **Option B** (Swift Concurrency). Aligns with Swift 6 direction, eliminates the weakSelf dance, and the Task cancellation API is cleaner than Timer.invalidate(). The debounce semantics are identical — a sleeping Task that gets cancelled on re-invocation.

**Files to Modify:**
- `DS3Drive/Views/Tray/ViewModels/DS3DriveViewModel.swift` — both `weakSelf` captures at lines 133 and 278, plus the Timer properties they reference (`transferStatsResetTimer`, `idleDebounceTimer`)

**Acceptance Criteria:**
- [ ] `xcodebuild clean build -scheme "DS3 Drive" SWIFT_STRICT_CONCURRENCY=complete` → zero `"Sending ... risks causing data races"` warnings
- [ ] `xcodebuild clean build -scheme "DS3 Drive" SWIFT_STRICT_CONCURRENCY=complete` → zero `"never mutated"` warnings for weakSelf
- [ ] Debounce behavior preserved: rapid `.sync` → `.idle` transitions still get coalesced with the 2s debounce
- [ ] Transfer stats reset still fires on the configured interval after idle
- [ ] If Option B is chosen, no orphaned Tasks after view model deinit (verify via Instruments or `deinit` log)
- [ ] SwiftLint passes without per-line suppressions

## Gap 28: Missing folder in Finder — S3 throttling causes incomplete root enumeration

**Severity:** **High** (data correctness — user sees incomplete view of their bucket; one folder is invisible in Finder)

**Symptom:**
The user's `personal-moschet` bucket has at least three top-level folders: `Automatic upload`, `Cubbit`, `Personal`. Finder only shows two: `Automatic upload` and `Cubbit`. The `Personal` folder is missing from the listing entirely — not just hidden, not just empty, but completely absent from the Finder column view.

**Root cause (confirmed via system logs):**

```
14:59:56.570 E  S3 listing failed, trying MetadataStore fallback for prefix nil:
                SotoCore.AWSResponseError error 1.
14:59:56.663 E  enumerateItems S3 error for drive E25A45D6-... prefix nil: SlowDown
15:00:13.871 I  BFS pass starting from prefix
15:01:20.809 E  S3 listing failed, trying MetadataStore fallback for prefix nil: ... error 1.
15:01:20.910 E  enumerateItems S3 error for drive ... prefix nil: SlowDown
15:01:41.746 E  BFS listing failed for prefix : ... error 1.
15:02:48.941 E  TrashS3Enumerator: S3 error SlowDown
```

S3 is returning **HTTP 503 with `SlowDown` error code** on `ListObjectsV2` calls for the bucket root. This is S3's request-rate throttling. Multiple parallel listers are hitting the same bucket simultaneously:

- `BreadthFirstIndexer` warming up the cache via recursive listings
- `S3Enumerator` handling Finder's `enumerateItems` calls for the root
- `TrashS3Enumerator` listing the trash subtree
- File-provider working set listings

When one of these gets throttled, the code falls back to `MetadataStore` — but the metadata store is empty/incomplete (the throttle hit before any successful listing populated it). The result: Finder receives a partial enumeration containing only the keys that were cached from a previous successful listing run, and `Personal` (a folder that wasn't in that earlier cache) is silently dropped.

**Two compounding bugs:**
1. **No retry with exponential backoff on `SlowDown`** — the code treats `SlowDown` as a hard failure and falls back immediately, instead of retrying with jittered backoff (which is the AWS-recommended response).
2. **No concurrency limit on S3 listings** — BFS, enumerator, trash, and working-set listings all run in parallel against the same bucket. AWS recommends limiting parallelism per prefix to avoid hot-partition throttling.

Plan 05-07's bug sweep introduced retry hardening for `fetchContents` with HTTP/2 `StreamClosed`, but didn't extend the same treatment to `listObjectsV2` calls, and didn't add a global semaphore on listings.

**Proposed Fix:**

### 1. Retry `SlowDown` with exponential backoff + jitter

Wrap `listObjectsV2` calls in a retry helper:
```swift
func listWithRetries(...) async throws -> ListObjectsV2Output {
    var attempt = 0
    let maxAttempts = 5
    while true {
        do {
            return try await s3.listObjectsV2(...)
        } catch let error as AWSResponseError where error.errorCode == "SlowDown" || error.statusCode == 503 {
            attempt += 1
            if attempt >= maxAttempts { throw error }
            let baseDelay = 0.5 * pow(2.0, Double(attempt))   // 0.5s, 1s, 2s, 4s, 8s
            let jitter = Double.random(in: 0...0.5)
            try await Task.sleep(for: .seconds(baseDelay + jitter))
            logger.warning("S3 SlowDown, retrying attempt \(attempt) after \(baseDelay + jitter)s")
        }
    }
}
```

Apply to all `listObjectsV2` call sites:
- `S3Enumerator.swift`
- `BreadthFirstIndexer.swift`
- `TrashS3Enumerator.swift`
- `S3Lib.swift` (any helper listing methods)

### 2. Concurrency semaphore on per-bucket listings

Introduce a per-drive (or per-bucket) `AsyncSemaphore` with `maxConcurrency = 4`. Every listing call must acquire the semaphore before issuing the request:
```swift
actor BucketListingLimiter {
    private let maxConcurrent = 4
    private var inFlight = 0
    private var waiters: [CheckedContinuation<Void, Never>] = []

    func acquire() async {
        if inFlight < maxConcurrent {
            inFlight += 1
            return
        }
        await withCheckedContinuation { cont in waiters.append(cont) }
    }

    func release() {
        if !waiters.isEmpty {
            waiters.removeFirst().resume()
        } else {
            inFlight -= 1
        }
    }
}
```

### 3. Smarter MetadataStore fallback

When `SlowDown` hits even after retries, the fallback should:
- NOT silently drop unknown keys
- Mark the listing as `partial` and surface an error in the drive row badge
- Schedule a delayed re-enumeration via `signalEnumerator(for:)` after a backoff
- Optionally show a user-visible "Bucket listing throttled — retrying" notification

### 4. Investigation sub-tasks

Run these to confirm the hypothesis:


## Gap 15: Global tray state disagrees with per-drive state

**Severity:** **High** (state correctness, user confusion)

**Symptom:**
The tray displays two disagreeing states at the same time:
- **Global state** (footer text + menu bar icon): shows **"Indexing"** with an animated / alternate icon
- **Header aggregate row**: shows **"All drives up to date"** (green checkmark)
- **Drive row** (`personal-moschet`): shows **green checkmark** with "6 min ago" — i.e., idle and fully synced
- **Recent Files panel**: shows one entry still stuck in "transferring" (related to Gap 14)

So the drive is idle, the header says everything is up to date, but the footer and menu bar icon still claim the app is indexing. The three sources of truth are not agreeing.

**Suspected root cause:**
There are (at least) two separate state machines driving what the tray shows:

1. **Per-drive state machine** — lives in `DS3DriveViewModel` / `DS3DriveManager`, driven by file-provider notifications and updated to `.idle` when the operation counter hits 0 after a debounce. This one correctly transitions to idle.

2. **Global "app state" machine** — probably lives in `AppStatusManager` (DS3Lib) or a separate indexer tracker, driven by the `BreadthFirstIndexer` lifecycle. This one reports `.indexing` during the initial BFS crawl and is supposed to transition to `.idle` when indexing finishes — but in this case, either:
   - The indexer never signals completion
   - The global state observer in the tray never receives the completion notification
   - A stuck Recent Files entry (Gap 14) is influencing the global status calculation
   - An orphaned counter in `NotificationsManager._activeOperations` never decrements back to 0 (see MEMORY.md: "each immediate `.sync` increments; each debounced `.idle`/`.error` decrements")

The menu bar icon is bound to the global state, and the footer text is bound to the same global state — so they move together (both show "Indexing") while per-drive rows correctly report idle.

**Proposed Fix:**

1. **Single source of truth for aggregate state.** Derive the aggregate tray status as a pure function of the per-drive states:
   ```
   aggregate = drives.reduce(.idle) { acc, drive in
       if drive.status == .error { return .error }
       if drive.status == .syncing && acc != .error { return .syncing }
       if drive.status == .indexing && acc == .idle { return .indexing }
       return acc
   }
   ```
   This way, if all drives are `.idle`, the aggregate is `.idle` — period. No independent global indexer state that can get out of sync.

2. **Audit `NotificationsManager._activeOperations` for leaks.** Per MEMORY.md the counter can diverge if:
   - A `.sync` increments but the corresponding `.idle`/`.error` is lost (extension crash, missed notification, debounce cancellation)
   - Parent folder error propagation (Gap from Phase 05) decrements twice or not at all
   
   Add invariant checks + a reset mechanism: on a known-good boundary (e.g., all enumerators idle, no in-flight operations in the extension), force the counter to 0.

3. **Menu bar icon binding.** Ensure the menu bar icon reads from the same derived aggregate state, not from a separate indexer flag.

4. **Footer text.** Bind the footer "Indexing/Idle/..." label to the derived aggregate. Pairs with Gap 13 (footer state icon) — same source.

5. **Watchdog.** If the global state stays in `.indexing` for > N seconds without any in-flight indexing operations, log a warning and auto-reset to `.idle`. This catches the leak case.

**Dependency:**
Pairs with Gap 14 (Recent Files state bug) — both are symptoms of the same class of state-tracking bugs in the extension/tray boundary. Fixing the NotificationsManager counter leak likely helps both.

**Files to Modify:**
- `DS3DriveProvider/NotificationsManager.swift` — audit counter lifecycle, add invariants, add watchdog
- `DS3Lib/Sources/DS3Lib/AppStatusManager.swift` — derive aggregate from per-drive states (if this is where global state lives)
- `DS3Drive/Views/Tray/ViewModels/DS3DriveViewModel.swift` — single `aggregateStatus` computed property
- `DS3Drive/DS3DriveApp.swift` — bind menu bar icon to `aggregateStatus`
- `DS3Drive/Views/Tray/Views/TrayMenuFooterView.swift` — bind footer label/icon to `aggregateStatus`
- `DS3DriveProvider/BreadthFirstIndexer.swift` — verify completion signal is always emitted (success, error, cancelled paths)

**Acceptance Criteria:**
- [ ] When all drives are `.idle`, the footer shows "Idle" and the menu bar icon shows the idle variant
- [ ] Menu bar icon, footer, header aggregate, and drive rows all agree at all times (single source of truth)

## Gap 14: Recent Files panel has duplicate entries, stuck transfers, and no clear action

**Severity:** **High** (real state bug, user-visible data correctness issue)

**Symptom:**
The Recent Files / Transfers side panel in the tray shows multiple bugs:

1. **Duplicate entries:** The same file (e.g., `IMG_9359.PNG`) appears twice in the panel — once with a stuck "transferring" spinner and again with a green checkmark ("done") directly below.

2. **Stuck "transferring" state:** Some entries remain in the transferring state indefinitely even after the file has actually completed syncing. The tracker never transitions them to `.completed`.

3. **No way to clear the panel:** Once an entry lands in the panel (correct or stuck), there is no UI affordance to remove it. Old entries accumulate until the panel is full of stale data.

**Root cause (likely):**
`DS3Lib/Sources/DS3Lib/Utils/RecentFilesTracker.swift` stores entries in an array and tracks them by index/append order. When the same file goes through multiple lifecycle events (e.g., `.started`, `.progress`, `.completed`, or a re-fetch after the file changes), new entries are appended instead of updating the existing one in place — either because:
- The identifier is computed differently between the "start" and "complete" notifications (e.g., object key vs. local path vs. file provider identifier)
- The `.started` → `.completed` transition fires on a different code path than the one that inserts the row, so the update target can't be found
- An `@unchecked Sendable` race between the extension (writer) and the UI (reader) lets two inserts land before the dedup check runs

Additionally, the tracker has no "finalization" hook — if the extension crashes mid-transfer or a notification is lost, the entry is never marked `.completed` or `.failed`, leaving it stuck.

**Proposed Fix — Three Todos:**

### Todo 1: Deduplicate entries by identifier

Replace the array-based storage with a dictionary keyed by a stable, canonical file identifier (prefer `NSFileProviderItemIdentifier.rawValue` = the full S3 key). Every update looks up the existing entry by key and mutates it in place.

```swift
// RecentFilesTracker.swift
private var entriesByKey: [String: RecentFileEntry] = [:]
private let lock = NSLock()

public func upsert(_ entry: RecentFileEntry) {
    lock.lock()
    defer { lock.unlock() }
    // Merge with existing entry if present (preserve earliest startedAt, latest status)
    if let existing = entriesByKey[entry.identifier] {
        entriesByKey[entry.identifier] = existing.merging(with: entry)
    } else {
        entriesByKey[entry.identifier] = entry
    }
    persist()
}

public var recentEntries: [RecentFileEntry] {
    lock.lock()
    defer { lock.unlock() }
    return Array(entriesByKey.values).sorted { $0.updatedAt > $1.updatedAt }
}
```

For the UI: expose a `Set`-backed or dict-backed collection so SwiftUI `ForEach` dedupes automatically via stable identifiers.

### Todo 2: Fix the stuck "transferring" state

1. Audit all call sites that create a `.transferring` entry — ensure every one has a corresponding `.completed` / `.failed` terminal call in both success and error paths of:
   - `fetchContents` (download)
   - `createItem` (upload)
   - `modifyItem` (re-upload)
   - Multipart upload completion callbacks
2. Add a timeout watchdog: any entry still in `.transferring` state > N seconds (e.g., 5 min) without a progress update is auto-transitioned to `.failed("timeout")` or removed.
3. On extension startup, sweep any entries left in `.transferring` from a previous session → mark them `.failed("interrupted")` or drop them.
4. Verify the identifier used in the `.started` call matches the identifier used in the `.completed` call — mismatches are the most likely culprit for the duplicate bug.

### Todo 3: Add a "Clear" button

Add a small "Clear" / "Clear all" button to the Recent Files panel header. Clicking it empties `entriesByKey` and persists the empty state.

```swift
// RecentFilesPanel.swift
HStack {
    Text("Recent Files").font(DS3Typography.heading)
    Spacer()
    Button("Clear") {
        recentFilesTracker.clearAll()
    }
    .buttonStyle(SubtleButtonStyle())
    .disabled(recentFilesTracker.recentEntries.isEmpty)
}
```

Also consider a per-entry "dismiss" affordance (small × button on hover) for fine-grained control.

**Files to Modify:**
- `DS3Lib/Sources/DS3Lib/Utils/RecentFilesTracker.swift` — dict-backed storage, upsert-by-key, clearAll, watchdog
- `DS3Lib/Sources/DS3Lib/Models/RecentFileEntry.swift` — add `updatedAt`, `merging(with:)` helper
- `DS3Lib/Tests/DS3LibTests/RecentFilesTrackerTests.swift` — add tests for dedupe, upsert, stuck-state cleanup, clearAll
- `DS3DriveProvider/FileProviderExtension+Create.swift` — verify `.completed` / `.failed` is always called
- `DS3DriveProvider/FileProviderExtension+Modify.swift` — same
- `DS3DriveProvider/FileProviderExtension.swift` (`fetchContents`) — same
- `DS3DriveProvider/S3Lib+Transfers.swift` — verify multipart upload completion always finalizes the entry
- `DS3Drive/Views/Tray/Views/RecentFilesPanel.swift` — add Clear button, per-entry dismiss, use stable identifier in ForEach

**Dependency:** None — this is a real bug and a data-correctness issue. Should be prioritized above cosmetic gaps.

**Acceptance Criteria:**
- [ ] A file that goes through `.started → .completed` appears **once** in the panel, not twice
- [ ] No entry remains in `.transferring` state after the actual transfer finishes

- [ ] Tests cover: dedupe by identifier, terminal state transitions, watchdog timeout, clearAll
- [ ] Swift 6 concurrency: all tracker mutations are serialized and Sendable-clean
