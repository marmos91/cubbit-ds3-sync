    **Parent folder stuck in progress (D-BUG-03):**
    The known issue is that when a child file operation fails, the parent folder's badge stays as "syncing" instead of showing "error". This happens because:
    1. The NotificationsManager increments the active operations counter when a sync starts
    2. On failure, the error notification decrements the counter
    3. But the parent folder's decoration is never updated to reflect the child error

    Fix approach:
    1. In FileProviderExtension's error handling paths (fetchContents catch, createItem catch, modifyItem catch), after reporting the file error:
       - Extract the parent identifier from the failed item (the directory containing the file)
       - Call `manager.signalEnumerator(for: parentIdentifier)` to trigger a re-enumeration of the parent folder
       - This will cause S3Enumerator to re-evaluate the folder's aggregate badge state

    2. In S3Item's decoration logic (the `decorations` property), ensure folder items compute their badge by checking children's syncStatus:
       - If any child has syncStatus "error" → folder shows error badge
       - If any child has syncStatus "syncing" → folder shows syncing badge
       - If all children have syncStatus "synced" → folder shows synced badge
       - This logic may already exist from plan 05-01 — verify and fix if incomplete

    3. In NotificationsManager, ensure the active operations counter correctly handles error states:
       - When an error decrements the counter and counter reaches 0, the status should be "error" not "idle"
       - Track whether any error occurred during the batch, and if so, set final status to error

    **HTTP/2 StreamClosed (-2005) hardening:**
    4. In S3Lib.swift and S3Lib+Transfers.swift, find all `fetchContents` and upload paths:
       - Verify `withRetries()` wrapper is present on all S3 operations that can get StreamClosed
       - If a retry count is hardcoded, ensure it's at least 3 retries with exponential backoff
       - Add a concurrency semaphore (DispatchSemaphore or Swift concurrency TaskGroup with maxConcurrency) to limit parallel fetchContents to 4 concurrent operations — this prevents overwhelming the HTTP/2 connection

    5. Review all error handling in extension methods for:
       - Bare `try` without `catch` (should always catch and return proper NSFileProviderError)
       - Force unwraps (`!`) on optional values from S3 responses
       - Missing `completionHandler` calls in error paths (leaked operations)
  </action>
